# Ebb Implement Task

Использовать этот скилл только для реализации ровно одной назначенной задачи из плана Ebb Orchestrator или одного подтверждённого кластера связанных замечаний.

Основной принцип: текущий агент является task-controller и не выполняет реализацию самостоятельно. Изменения кода, тестов и документации, воспроизведение ошибок, запуск проверок, self-review и исправления выполняются только специализированными субагентами с минимальным изолированным контекстом.

Цель такой схемы — не загружать контекст task-controller большими исходными файлами, diff, логами тестов и деталями расследования. Полные результаты должны сохраняться в artifacts/files, а между агентами передаваться преимущественно пути к ним и короткие структурированные отчёты.

## Роли

- **Task-controller** — текущий агент. Читает управляющие инструкции и назначенную задачу, определяет границы работы, зависимости внутри задачи, ведёт локальный ledger, запускает и перезапускает субагентов и принимает их краткие статусы.
- **Implementer** — свежий субагент, который выполняет конкретную реализацию по TDD, запускает целевые проверки и делает self-review.
- **Reviewer** — отдельный свежий субагент, который независимо проверяет соответствие задаче, качество реализации, тесты и scope.
- **Fixer** — свежий субагент, который исправляет только подтверждённые findings или конкретную воспроизводимую ошибку.
- **Verification agent** — при необходимости отдельный свежий субагент для финального набора проверок по задаче.

Implementer, Reviewer, Fixer и Verification agent никогда не создают собственных субагентов.

## Совместимость с `ebb-execute-plan`

При запуске этого скилла из `ebb-execute-plan` разрешён ровно один дополнительный уровень вложенности:

`plan-controller → task-controller → worker/reviewer`

Это единственное допустимое исключение из общего запрета nested subagents для данного workflow.

- `plan-controller` отвечает за весь план и назначает одну задачу task-controller.
- `task-controller` отвечает только за эту задачу и может создавать Implementer/Reviewer/Fixer/Verification agent.
- Любой worker/reviewer обязан получить явный запрет на создание дальнейших агентов.
- Глубина вложенности больше этого уровня запрещена.
- Одновременно во всём workflow не должно работать более 2 субагентов, включая дочерних агентов task-controller.

## Жёсткие правила

- Сначала прочитать `.hermes.md`, затем полностью прочитать только назначенную задачу и необходимые для неё управляющие требования.
- Работать только в текущем worktree/ветке. Не создавать дочерние worktree.
- Task-controller НЕ ИМЕЕТ ПРАВА самостоятельно редактировать production/test/docs-файлы, исправлять код, писать тесты, выполнять рефакторинг или создавать commit.
- Любое изменение файлов в рамках задачи выполняется исключительно Implementer/Fixer-субагентом.
- Task-controller не должен читать большие исходные файлы, полный diff или длинные test/build logs, если это можно поручить субагенту и получить краткий отчёт.
- Никогда не запускать более 2 субагентов одновременно.
- Обычно одновременно работает только один Implementer/Fixer. Параллельная реализация разрешена только для действительно независимых частей одной задачи с непересекающимися файлами и интерфейсами.
- Reviewer не должен быть тем же агентом, который реализовывал или исправлял проверяемые изменения.
- Self-review Implementer-а не заменяет независимый review.
- Не изменять файлы, не относящиеся к назначенной задаче.
- Не изменять файлы, принадлежащие другой задаче плана, без эскалации к plan-controller.
- Не выполнять merge/push/tag/release.
- Не считать отсутствие ответа или verdict reviewer-а успешной проверкой.
- Не заявлять о завершении без подтверждённых test/verification evidence.
- Все новые или изменённые production-комментарии должны быть на русском языке и использовать JSDoc там, где это требуется.

## Подготовка задачи

1. Зафиксировать текущие branch, HEAD и состояние working tree.
2. Прочитать `.hermes.md` и назначенную задачу.
3. Определить допустимый file scope, обязательные проверки, связанные спецификации и публичные интерфейсы.
4. Не загружать в собственный контекст большие связанные файлы без необходимости. Вместо этого включить их пути в task brief и поручить чтение Implementer-у.
5. Создать локальный ledger задачи со статусами `READY / RUNNING / REVIEW / FIX / VERIFY / DONE / BLOCKED`.
6. Подготовить минимальный task brief, содержащий:
   - точный текст требований задачи;
   - разрешённый file scope;
   - ссылки/пути на необходимые spec/code/tests;
   - известные входные и выходные интерфейсы;
   - обязательные проверки;
   - ограничения из `.hermes.md`, относящиеся к задаче;
   - путь к report/artifact.
7. Перед первым изменением по возможности поручить Implementer-у запуск focused baseline tests и сохранение результата в artifact.

## Цикл реализации

Для каждого изменения поведения Implementer обязан выполнять TDD-последовательность:

1. доказать или воспроизвести требуемое поведение/ошибку;
2. написать или обновить regression test;
3. когда это практически возможно, запустить тест и подтвердить ожидаемое падение;
4. реализовать минимальное корректное изменение;
5. обновить русский JSDoc, если изменился публичный контракт или инвариант;
6. запустить focused test;
7. запустить соседние релевантные тесты;
8. запустить `git diff --check`;
9. провести self-review своего diff;
10. сохранить полный отчёт, diff/логи и test evidence в task artifacts;
11. вернуть task-controller только краткий статус: результат, изменённые файлы, проверки, путь к отчёту и обнаруженные риски.

Task-controller не повторяет эти действия самостоятельно.

## Review loop

После успешного отчёта Implementer-а:

1. Перевести задачу в `REVIEW`.
2. Запустить свежего Reviewer-субагента.
3. Передать Reviewer-у task brief, BASE/HEAD или artifact с diff, implementer report и необходимые spec paths.
4. Reviewer обязан независимо проверить:
   - соответствие точным требованиям задачи;
   - отсутствие выхода за разрешённый scope;
   - корректность тестов и наличие test evidence;
   - качество реализации и отсутствие очевидных регрессий;
   - корректность JSDoc/комментариев при изменении публичных контрактов;
   - отсутствие замаскированных ошибок, ослабленных assertions или отключённых проверок.
5. Reviewer возвращает только `APPROVED` либо `CHANGES_REQUIRED` с кратким списком findings и путём к полному review report.
6. При `CHANGES_REQUIRED` перевести задачу в `FIX` и запустить свежего Fixer-субагента.
7. Fixer получает только исходный task brief, подтверждённые findings, необходимые artifact paths и минимальный дополнительный контекст.
8. После исправления запустить свежего scoped Reviewer-а. Не использовать исходного Implementer-а как reviewer.
9. Повторять fix/re-review до `APPROVED` или срабатывания breaker.

## Политика ошибок и перезапуска субагентов

Ошибку субагента всегда отличать от подтверждённой ошибки реализации.

- **Crash / timeout / tool error / потерянный ответ:** отметить попытку как инфраструктурно неуспешную и запустить свежего субагента той же роли. Не заставлять task-controller самостоятельно продолжать его работу.
- **`NEEDS_CONTEXT` или эквивалент:** добавить только недостающий контекст в task brief или отдельный context artifact и запустить свежего агента.
- **Ошибка реализации / падающий regression test после изменения:** запустить свежего Fixer-а с task brief и artifact с ошибкой.
- **Повторяющаяся ошибка рассуждения:** после 2 неуспешных implementation/fix-попыток следующего свежего агента запускать на более мощной доступной модели и по возможности дополнительно сузить проблему.
- **Reviewer не вернул однозначный verdict:** review считается неуспешным; запустить свежего Reviewer-а.
- **Reviewer обнаружил проблему в собственном review artifact или противоречит задаче:** запустить свежего Reviewer-а с теми же исходными требованиями; task-controller не разрешает спор самостоятельным анализом большого diff.
- **Breaker:** после 5 implementation/fix-попыток для одной и той же подтверждённой проблемы перевести задачу в `BLOCKED`, сохранить reports/logs и вернуть управление plan-controller или пользователю с точной причиной.

Каждая новая попытка получает минимальный контекст: task brief, относящиеся к попытке artifact paths, текущие BASE/HEAD при необходимости и краткое описание причины предыдущей неудачи. Не передавать полный transcript сессии.

## Экономия контекста

- Не вставлять полный diff в ответы субагентов. Сохранять его в файл и возвращать путь.
- Не вставлять длинные логи тестов/build в чат. Сохранять их в artifact и возвращать итоговые строки/статус.
- Не передавать новому агенту историю всех прошлых попыток. Передавать только последний релевантный failure report и ledger.
- Не заставлять Reviewer повторно читать весь план. Он получает только task brief и связанные спецификации.
- Не заставлять Implementer читать нерелевантные части репозитория «для понимания проекта».
- Объединять несколько мелких однотипных изменений внутри одной задачи в один implementation dispatch, если они не требуют независимого reasoning.
- При необходимости исследования большого участка кода использовать отдельного investigation-субагента, который сохраняет выводы в короткий context artifact; task-controller читает только summary.
- Предпочитать пути к файлам и структурированные reports повторному копированию содержимого между агентами.

## Финальная проверка задачи

После `APPROVED`:

1. Если задача требует более широкого набора проверок, запустить отдельного Verification agent.
2. Verification agent выполняет только проверки, относящиеся к этой задаче и её непосредственным интеграционным границам.
3. Полный вывод сохраняется в artifact; task-controller получает краткий verdict.
4. Если verification подтверждает новую проблему, перевести задачу в `FIX` и продолжить обычный fix/re-review цикл.
5. Если все обязательные проверки пройдены, перевести задачу в `DONE`.
6. Commit создаётся только если этого требует вызывающий workflow/план; его создаёт назначенный субагент, а не task-controller.

## Результат

Вернуть вызывающему агенту или пользователю краткий структурированный результат:

- статус `DONE` или `BLOCKED`;
- branch и HEAD;
- изменённые файлы;
- выполненные проверки и их итог;
- reviewer verdict;
- количество implementation/fix/retry попыток;
- пути к implementation/review/verification artifacts;
- подтверждённые оставшиеся риски или blocker.

Не возвращать полные diff и длинные логи, если их явно не запросили.

## Запрещённые сокращения процесса

Не выполнять реализацию task-controller’ом. Не пропускать TDD без зафиксированной причины, не игнорировать падающие тесты, не ослаблять assertions, не отключать lint/type/JSDoc/security-правила, не скрывать ошибки, не придумывать PASS-результаты, не обходить независимый review, не принимать отсутствие verdict за одобрение, не расширять scope за пределы назначенной задачи и не использовать одного и того же агента одновременно как implementer и reviewer.
