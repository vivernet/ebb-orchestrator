# Ebb Debug Issue

Использовать этот скилл только при диагностике и устранении ошибки, бага, регрессии, падения теста, проблемы сборки, интеграции, конфигурации или другого неожиданного поведения в Ebb Orchestrator.

Основной принцип:

> **Никаких исправлений до подтверждённого расследования root cause. Никаких заявлений об исправлении без свежей независимой verification.**

Текущий агент является **debug-controller**. Он не расследует большие участки кода самостоятельно и не исправляет production/test/docs-файлы. Его задача — организовать воспроизводимое расследование, собрать независимые доказательства через субагентов, подтвердить root cause, передать исправление в `ebb-implement-task`, организовать финальный review и только после свежей verification считать проблему устранённой.

Цели workflow:

1. не угадывать причину по симптомам;
2. найти источник проблемы, а не замаскировать проявление;
3. минимизировать расход контекста родительского агента;
4. исправить проблему через TDD;
5. независимо проверить качество исправления;
6. доказать устранение исходного симптома и отсутствие очевидной регрессии.

## Входные данные

Пользователь может передать любые доступные сведения:

- текст ошибки;
- stack trace;
- failing test;
- скриншот или лог;
- шаги воспроизведения;
- ожидаемое и фактическое поведение;
- имя компонента/файла;
- описание «раньше работало, теперь нет»;
- сведения о среде;
- неполное описание симптома.

Неполнота входных данных не является основанием сразу задавать пользователю вопросы. Сначала необходимо поручить субагентам извлечь максимум фактов из репозитория, Git-истории, тестов, логов и доступной среды. Запрашивать пользователя следует только тогда, когда отсутствующий внешний факт действительно невозможно получить из проекта или воспроизвести самостоятельно.

## Архитектура ролей

### Debug-controller

Текущий агент.

Разрешено:

- читать `.hermes.md`, пользовательское сообщение и управляющую метаинформацию;
- создавать и обновлять debug ledger;
- определять этапы расследования;
- формировать минимальные briefs;
- запускать, перезапускать и эскалировать субагентов;
- читать краткие structured summaries;
- проверять минимально необходимую Git-метаинформацию;
- принимать workflow-решения на основе доказательств субагентов.

Запрещено:

- самостоятельно исправлять production/test/docs-файлы;
- самостоятельно выполнять полноценное расследование большого участка кода;
- читать полный diff или длинные логи, если их можно отдать субагенту;
- придумывать root cause без доказательств;
- считать отчёт implementer-а доказательством исправления.

### Reproducer

Свежий субагент, который пытается надёжно воспроизвести проблему и зафиксировать baseline.

Он определяет:

- точную команду/сценарий воспроизведения;
- наблюдаемый симптом;
- exit code;
- релевантный stack trace/error code;
- минимальные условия возникновения;
- стабильность воспроизведения;
- работает ли аналогичный соседний сценарий.

Reproducer не исправляет проблему.

### Investigator

Свежий субагент для root-cause investigation.

Он:

- читает полные сообщения об ошибках и stack traces;
- трассирует поток данных назад к источнику;
- проверяет недавние изменения, конфигурацию, зависимости и environment;
- сравнивает сломанный путь с работающим аналогом;
- для многоуровневых систем определяет границу, на которой данные/состояние становятся некорректными;
- формирует конкретные гипотезы и проверяет по одной переменной за раз;
- сохраняет evidence и выводы в investigation artifact.

Investigator не должен вносить исправление production behavior до подтверждения root cause.

### Diagnosis Reviewer

Отдельный свежий субагент, который независимо проверяет диагноз.

Он не должен быть Reproducer или Investigator из текущего цикла.

Допустимые verdict:

- `ROOT_CAUSE_CONFIRMED`
- `INSUFFICIENT_EVIDENCE`
- `ALTERNATIVE_CAUSE_FOUND`
- `ARCHITECTURAL_RISK`

### Task-controller (`ebb-implement-task`)

После подтверждения root cause debug-controller запускает отдельного task-controller через `ebb-implement-task`.

Именно этот workflow реализует regression test, fix, task review, fix/re-review loop и scoped verification.

### Final Bug Reviewer

Свежий независимый субагент после реализации. Он оценивает исправление именно как bugfix целиком, а не только как выполненную implementation task.

### Final Verification Agent

Свежий субагент, который выполняет финальные команды проверки и доказывает фактическое устранение исходной проблемы.

## Ограничение вложенности и параллелизма

Разрешена следующая максимальная структура:

`debug-controller → investigation/review agent`

или во время исправления:

`debug-controller → ebb-implement-task task-controller → worker/reviewer`

Глубже вложенность запрещена.

Правила:

- одновременно во всём workflow не должно работать более 2 субагентов;
- когда активен `ebb-implement-task` task-controller, debug-controller не запускает других субагентов: второе доступное место резервируется для его worker/reviewer;
- Reproducer и Investigator допускается запускать параллельно только если они не мешают друг другу и не изменяют одни и те же файлы;
- любой leaf-agent получает явный запрет создавать собственных субагентов.

## Жёсткие правила

- Сначала прочитать `.hermes.md`.
- Работать только в текущем worktree/ветке.
- Не создавать дочерние worktree.
- Debug-controller НЕ ИМЕЕТ ПРАВА самостоятельно исправлять код, тесты или документацию.
- **NO FIX WITHOUT ROOT CAUSE INVESTIGATION.**
- Не считать первое правдоподобное объяснение root cause.
- Не объединять несколько неподтверждённых гипотез в один fix.
- Проверять по одной существенной переменной за раз.
- Сначала получить воспроизводимый failure/evidence, затем regression test, затем минимальный fix.
- Не изменять нерелевантные файлы и не выполнять opportunistic refactoring.
- Не ослаблять тесты, assertions, типизацию, lint/security/JSDoc-правила ради зелёного результата.
- Не скрывать ошибку retry/timeout/fallback-механизмом, если это не является подтверждённым корректным решением root cause.
- Не выполнять merge/push/tag/release без явного запроса пользователя.
- Не заявлять `FIXED`, `DONE`, «исправлено», «тесты проходят» или эквивалент без свежего verification evidence.
- Все новые или изменённые production-комментарии должны быть на русском языке и использовать JSDoc там, где это требуется.

## Debug workspace и ledger

Для каждого запуска создать отдельный debug workspace/artifact directory, если среда это позволяет.

Хранить там:

- `issue-brief.md` — исходный симптом и известные факты;
- `progress.md` — debug ledger;
- `reproduction-report.md`;
- `investigation-*.md`;
- `diagnosis-review.md`;
- `fix-brief.md`;
- implementation/review artifacts из `ebb-implement-task`;
- `final-review.md`;
- `verification-report.md`;
- при необходимости полные логи, diff и диагностические данные.

Ledger отслеживает как минимум:

`INTAKE / REPRODUCE / INVESTIGATE / DIAGNOSIS_REVIEW / ROOT_CAUSE_CONFIRMED / IMPLEMENT / REVIEW / VERIFY / DONE / BLOCKED`

Для каждой попытки записывать:

- роль и id агента;
- номер попытки;
- гипотезу;
- evidence artifact;
- verdict;
- BASE/HEAD при изменениях;
- причину retry/escalation;
- подтверждённые решения.

Ledger является источником истины при compaction/restart. Не повторять завершённые этапы без новой причины.

# Workflow

## Phase 0 — Intake и baseline

1. Зафиксировать:
   - branch;
   - HEAD;
   - `git status`;
   - исходное сообщение пользователя;
   - доступные error/log/test данные.
2. Создать `issue-brief.md`.
3. Отделить **факты** от **предположений**.
4. Не формулировать fix.
5. Определить минимальный набор investigation paths:
   - воспроизведение;
   - трассировка root cause;
   - при необходимости Git/config/environment investigation.

Если пользователь уже дал точную failing command, всё равно необходимо независимо воспроизвести её свежим запуском, если среда позволяет.

## Phase 1 — Воспроизведение

Запустить Reproducer.

Он обязан:

1. выполнить точный или максимально близкий сценарий;
2. зафиксировать свежий результат и exit code;
3. минимизировать reproduction до наименьшего устойчивого сценария;
4. проверить, воспроизводится ли проблема повторно;
5. указать, какие условия делают её появление/исчезновение стабильным;
6. сохранить полный лог в artifact;
7. вернуть debug-controller краткий status:
   - `REPRODUCED`
   - `INTERMITTENT`
   - `NOT_REPRODUCED`
   - `BLOCKED_BY_ENVIRONMENT`

Если `NOT_REPRODUCED`, не угадывать исправление. Перейти к сбору дополнительных evidence: история изменений, environment/config difference, существующие failing tests, telemetry/logs.

## Phase 2 — Root-cause investigation

Запустить Investigator.

Применять систематический порядок:

1. **Ошибки и stack trace**
   - прочитать полностью;
   - зафиксировать точку падения;
   - отделить место проявления от возможного источника.

2. **Recent changes**
   - изучить релевантные Git diff/commits;
   - зависимости;
   - конфиги;
   - migration/environment изменения;
   - если это подтверждённая регрессия с неизвестным виновным commit и история позволяет, использовать `git bisect` через отдельного investigation-субагента вместо ручного перебора истории.

3. **Data/control flow tracing**
   - идти от неправильного значения/состояния назад;
   - определить, кто его создал;
   - продолжать до первой точки, где состояние становится неправильным.

4. **Working vs broken**
   - найти максимально похожий рабочий путь;
   - перечислить фактические различия;
   - не отбрасывать различия без проверки.

5. **Component boundaries**
   Для multi-component цепочки проверить вход/выход каждой границы:
   - request → router;
   - router → service;
   - service → provider/database;
   - config/environment → runtime;
   - build → generated artifact;
   - аналогичные реальные границы проекта.

6. **Hypothesis**
   Сформулировать ровно одну проверяемую гипотезу:

   `Предполагаемый root cause: X, потому что evidence Y и Z. Если гипотеза верна, проверка Q должна дать результат R.`

7. **Minimal hypothesis test**
   - одна переменная за попытку;
   - минимальный диагностический experiment;
   - не превращать experiment в постоянный fix;
   - временную instrumentation/diagnostic modification обязательно откатить после получения evidence, если её сохранение не является отдельно обоснованной частью исправления;
   - сохранить результат.

Если гипотеза не подтверждена — записать её как rejected и сформулировать новую. Не наращивать поверх неё случайные исправления.

## Phase 3 — Независимое подтверждение диагноза

После появления предполагаемого root cause запустить свежего Diagnosis Reviewer.

Передать только:

- `issue-brief.md`;
- reproduction report;
- investigation artifacts;
- пути к необходимым исходным/spec-файлам;
- сформулированную гипотезу.

Reviewer обязан ответить:

### `ROOT_CAUSE_CONFIRMED`

Только если evidence объясняет:

- почему возникает исходный симптом;
- где появляется неправильное состояние;
- почему это является источником, а не только местом падения;
- каким экспериментом гипотеза подтверждена;
- почему предложенная fix boundary соответствует источнику проблемы.

### `INSUFFICIENT_EVIDENCE`

Если данных недостаточно. Вернуться в `INVESTIGATE` с конкретным списком недостающих доказательств.

### `ALTERNATIVE_CAUSE_FOUND`

Если evidence лучше объясняется другой причиной. Вернуться в `INVESTIGATE` с новой гипотезой.

### `ARCHITECTURAL_RISK`

Если исправление симптома требует затронуть фундаментальную архитектуру или 3 последовательные разумные гипотезы/fix-направления провалились.

В этом случае не продолжать бесконечные локальные patches. Подготовить отдельный architectural finding и либо:
- выполнить дополнительное архитектурное investigation;
- либо вернуть `BLOCKED` с точным объяснением, если дальнейшее решение требует решения пользователя/изменения scope.

## Phase 4 — Формирование bugfix brief

Только после `ROOT_CAUSE_CONFIRMED`.

Создать минимальный `fix-brief.md`:

- исходный пользовательский симптом;
- точный reproduction;
- подтверждённый root cause;
- evidence paths;
- ожидаемое корректное поведение;
- точная fix boundary;
- разрешённый file scope;
- обязательный regression test;
- команды RED/GREEN verification;
- соседние тесты;
- необходимые lint/type/build/security gates;
- запрет unrelated refactoring;
- known risks.

Fix brief не должен содержать полный transcript расследования.

## Phase 5 — Реализация через `ebb-implement-task`

Запустить свежего task-controller с процедурой `ebb-implement-task`.

Передать ему `fix-brief.md` как единственный источник требований и пути к необходимым evidence artifacts.

Обязательные требования к implementation:

1. создать минимальный regression test, который воспроизводит баг;
2. запустить его **до fix** и подтвердить ожидаемый RED;
3. реализовать минимальное исправление именно root cause;
4. получить GREEN на regression test;
5. запустить соседние релевантные tests;
6. выполнить `git diff --check`;
7. провести независимый task review;
8. исправить подтверждённые findings через Fixer;
9. выполнить scoped verification согласно `ebb-implement-task`.

Если `ebb-implement-task` возвращает `BLOCKED`, debug-controller не подменяет его и не дописывает fix самостоятельно. Вернуться либо в investigation, либо завершить `BLOCKED` с evidence.

## Phase 6 — Whole-bug review

После успешного `ebb-implement-task` запустить свежего Final Bug Reviewer.

Reviewer получает:

- issue brief;
- confirmed diagnosis;
- fix brief;
- BASE/HEAD или diff artifact;
- task review report;
- test evidence.

Он проверяет не только стиль кода, но и причинную связь:

1. fix действительно устраняет подтверждённый root cause;
2. это не symptom suppression;
3. regression test ловит исходный дефект, а не implementation detail;
4. scope минимален;
5. нет скрытого weakening тестов/валидации;
6. error handling не маскирует ошибки;
7. нет очевидного нового failure path;
8. соблюдены требования `.hermes.md`;
9. нет нерелевантных изменений.

Verdict:

- `APPROVED`
- `CHANGES_REQUIRED`
- `DIAGNOSIS_INVALIDATED`

При `CHANGES_REQUIRED` сформировать findings artifact и отправить fresh Fixer через `ebb-implement-task`/его fix-loop, после чего выполнить новый scoped review.

При `DIAGNOSIS_INVALIDATED` вернуться в Phase 2. Не пытаться «докрутить» текущий fix.

## Phase 7 — Fresh final verification

После `APPROVED` запустить отдельного Final Verification Agent.

Он обязан получить **свежие** результаты, а не доверять отчётам implementer/reviewer.

Минимальный набор:

1. повторить исходный reproduction;
2. запустить regression test;
3. запустить соседние релевантные tests;
4. выполнить проектные проверки, применимые к изменённой области:
   - typecheck;
   - lint;
   - build;
   - integration/E2E;
   - security/static checks;
5. выполнить `git diff --check`;
6. проверить exit codes и количество failures;
7. сохранить полный output в `verification-report.md`/log artifacts.

Проверка считается успешной только если свежие evidence подтверждают все заявляемые факты.

Если исходный баг timing/environment-dependent, verification должна повторить сценарий достаточное число раз или использовать condition-based проверку вместо произвольного `sleep`.

Если финальная verification выявила новую связанную проблему:
- перевести workflow в `IMPLEMENT`;
- создать отдельный finding;
- выполнить fix/re-review;
- затем полностью повторить Final Verification.

## Phase 8 — Финальный статус

`DONE` разрешён только если одновременно выполнены все условия:

- проблема воспроизведена или получено эквивалентное надёжное evidence;
- root cause подтверждён независимым Diagnosis Reviewer;
- существует regression coverage либо явно задокументирована техническая причина, почему автоматизация невозможна;
- implementation завершён через `ebb-implement-task`;
- task-level review пройден;
- whole-bug review = `APPROVED`;
- свежая final verification подтверждает устранение исходного симптома;
- обязательные применимые gates прошли;
- нет скрытых blockers.

Иначе вернуть фактический статус: `BLOCKED`, `PARTIALLY_VERIFIED` или `NOT_REPRODUCED`, а не заявлять об исправлении.

## Политика retries и escalation

Ошибку агента отличать от ошибки гипотезы или кода.

### Ошибка субагента

`crash / timeout / tool error / потерянный ответ`

- не продолжать его работу вручную;
- сохранить доступные artifacts;
- запустить свежего агента той же роли;
- передать минимальный brief + актуальные paths.

### `NEEDS_CONTEXT`

- определить конкретно недостающий факт;
- добавить только его;
- запустить свежего агента;
- не передавать весь transcript.

### Неудачная гипотеза

- не считать инфраструктурным retry;
- записать hypothesis как rejected;
- сформулировать новую на основе evidence.

### Повторяющиеся неудачи

- после 2 неудачных попыток одной роли использовать более мощную доступную модель;
- после 3 разумных fix/hypothesis направлений, каждое из которых раскрывает новую связанную проблему, обязательно проверить архитектурное предположение вместо продолжения patching;
- после 5 неуспешных попыток одного и того же этапа с одной причиной срабатывает breaker → `BLOCKED`.

Никогда не понижать требования для прохождения breaker.

## Выбор модели и экономия токенов

Если runtime позволяет выбирать модель, указывать её явно при каждом dispatch.

Рекомендация:

- Reproducer и механические проверки → самая дешёвая модель, способная надёжно работать с repo/tools;
- Investigator → средняя/сильная модель в зависимости от размера и связности проблемы;
- Diagnosis Reviewer → не слабее Investigator;
- `ebb-implement-task` → выбирать модель по сложности fix;
- Final Bug Reviewer → сильная модель для сложных/многофайловых исправлений;
- Verification Agent → дешёвая/средняя модель, если проверки механические.

Экономия контекста обязательна:

- полные логи сохранять в файлы;
- полные diff сохранять в artifacts;
- debug-controller получает только summary + verdict + paths;
- каждый новый агент получает только контекст своей роли;
- не передавать историю всех неудачных попыток;
- не заставлять reviewer читать весь репозиторий без причины;
- не заставлять task-controller перечитывать investigation transcript;
- повторно использовать подтверждённые artifacts вместо копирования их содержимого в prompt.

## Когда допустим внешний research

Если проблема связана с внешней библиотекой, SDK, API, инструментом или поведением версии:

- сначала определить точную используемую версию;
- поручить отдельному research/investigation агенту проверить актуальную официальную документацию или release notes;
- отличать документированное поведение от предположений;
- сохранить ссылки/выводы в evidence artifact;
- не обновлять dependency «наугад» без подтверждения, что версия связана с root cause.

## Особые случаи

### Проблема не воспроизводится

Не делать случайный fix.

Собрать:

- environment differences;
- версии;
- recent changes;
- flaky/timing evidence;
- existing logs;
- telemetry;
- race-condition indicators.

При необходимости добавить диагностическое логирование/monitoring через отдельную контролируемую задачу, не меняющую бизнес-поведение.

### Проблема внешняя

Если root cause подтверждён во внешнем сервисе/зависимости:

- задокументировать evidence;
- определить корректную защиту: retry, timeout, circuit breaker, validation, graceful error;
- не представлять workaround как исправление внешнего root cause;
- verification должна проверять именно обещанное локальное поведение.

### Security-sensitive issue

Не публиковать секреты и чувствительные данные в reports/logs. Редактировать/маскировать их до сохранения artifacts.

### Несколько root causes

Не объединять всё в один гигантский fix.

Разделить на независимые fix units с собственными:

- root-cause evidence;
- regression test;
- implementation;
- review;
- verification.

Последовательность определяет debug-controller.

## Запрещённые сокращения процесса

Запрещено:

- сразу предлагать fix по тексту ошибки без investigation;
- чинить место падения без трассировки источника;
- применять несколько гипотез одним изменением;
- менять тест так, чтобы он перестал видеть баг;
- добавлять catch/retry/timeout только ради исчезновения ошибки;
- исправлять код debug-controller’ом;
- доверять словам implementer-а «готово» без независимого review;
- доверять review без свежей verification;
- принимать старый test run как доказательство текущего HEAD;
- скрывать failing tests;
- ослаблять assertions;
- отключать проверки;
- расширять scope «раз уж мы здесь»;
- придумывать PASS;
- считать отсутствие verdict одобрением.

## Финальный отчёт

Вернуть пользователю или вызывающему workflow краткий структурированный результат:

- статус: `DONE / BLOCKED / PARTIALLY_VERIFIED / NOT_REPRODUCED`;
- исходный симптом;
- подтверждённый root cause;
- краткое описание fix;
- изменённые файлы;
- regression test;
- выполненные проверки и exit codes;
- task-review verdict;
- whole-bug-review verdict;
- количество retry/escalation;
- branch и HEAD/commit;
- пути к ключевым artifacts;
- известные оставшиеся риски/ограничения.

Не вставлять полный diff или длинные логи, если их явно не запросили.
