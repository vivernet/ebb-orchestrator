# Ebb AI Development Orchestrator — Final V1 Audit & Hardening Plan (Перевод)

> **Для агентов-исполнителей:** ОБЯЗАТЕЛЬНЫЙ ПОДСКЛЮЧ: Используйте `superpowers:subagent-driven-development`, где полезны независимые проходы ревью. Этот план — план аудита и устранения недостатков, а не план обычной реализации функциональности. Не объявляйте завершение, пока не пройдут все финальные ворота в этом документе.

## Цель
Выполнить аудит всего проекта Ebb AI Development Orchestrator после объединения планов 1–6, выявить пробелы в реализации по сравнению с утверждённым дизайном и каноническими планами, устранить дефекты в рамках утверждённой архитектуры и оставить репозиторий в состоянии, готовом к релизу и полностью верифицированном.

## Архитектура
Аудит рассматривает утверждённую спецификацию дизайна и канонические планы 1–6 как авторитетный источник. Сначала строится инвентарь реализации на основе доказательств, затем проверяется архитектура, инварианты предметной области, безопасность, поведение Git/worktree, интеграция с Hermes runtime, персистентность/восстановление, UI/API, интеграция с GitHub, тесты, миграции, конкуррентность, бюджеты, конфигурация и операционное качество. Обнаружения, которые можно исправить без изменения утверждённой архитектуры, исправляются автономно; изменения архитектуры/объёма преобразуются в явные предложения и не реализуются молча.

## Технический стек
TypeScript, Node.js, pnpm, Fastify, React/Vite, Vitest, SQLite, Git worktrees, Hermes runtime, GitHub adapter.

## Глобальные ограничения

- Все пользовательские ответы, обновления прогресса, результаты аудита, объяснения, выводы, отчёты и видимые рассуждения должны быть написаны на русском языке.
- Идентификаторы исходного кода, пути файлов, команды, имена API, имена схем/свойств, Git-ссылки, сообщения об ошибках и канонические технические термины сохраняйте без изменений, если перевод снизил бы точность.
- При цитировании существующей английской документации или комментариев кода сохраняйте оригинальный текст, где точная формулировка важна, но объясняйте его значение на русском.

- Работайте только в выделенной ветке/worktree аудита, созданной из текущего чистого `master`.
- Не выполняйте аудит напрямую в `master`.
- Не пушьте, не открывайте PR, не объединяйте, не делайте rebase, не делайте reset, force-clean и не удаляйте worktrees, пока это явно не запрошено после завершения аудита.
- Не изменяйте молча утверждённую архитектуру, область продукта, модель ролей, модель безопасности, семантику рабочих процессов или модель персистентности.
- Исправляйте дефекты, недостающие подключения, неполные тесты, некорректную типизацию, мёртвый код, дублирование, небезопасное поведение и проблемы качества, которые явно нарушают или не удовлетворяют утверждённый дизайн.
- Если предлагаемое исправление существенно меняет архитектуру, поведение продукта, семантику рабочих процессов, политику безопасности или область, создайте предложение вместо реализации.
- Deterministic-first остаётся обязательным: если обычный код может надёжно принять решение, не вводите зависимость от LLM.
- `master` — каноническая ветка по умолчанию для этого репозитория, если конфигурация проекта явно не переопределяет её для управляемого внешнего проекта.
- Не ослабляйте ESLint, строгость TypeScript, тесты, границы безопасности или правила одобрения только для прохождения контрольных точек качества.
- Не решайте ошибки типов с помощью широких `any`, небезопасных приведений или утверждений не-null, если инвариант явно не доказан.
- Не удаляйте тесты только потому, что они падают.
- Не добавляйте обходные пути только для сокрытия устаревших импортов, когда канонический API может быть исправлен.
- Каждое исправление должно иметь регрессионный тест, если изменение касается только документации или чистки мёртвого кода с существующим покрытием.
- Предпочитайте небольшие сфокусированные коммиты, сгруппированные по корневой причине.
- Финальное завершение требует чистой рабочей tree.

## Phase 2 — Прослеживание критических сквозных потоков

Проверить эти потоки, читая код и запуская тесты.

### Flow A — Standalone Task

Проследить:

```text
Request
→ Task
→ scheduler eligibility
→ runtime dispatch
→ Developer
→ Reviewer
→ QA
→ Integration
→ FINAL_MERGE approval
→ deterministic MergeService
→ RELEASED
```

Проверить:

- правильные переходы состояний;
- одобрения на правильных границах;
- отсутствие прямой мутации AI состояния предметной области;
- правильные владение worktree/веткой;
- Developer не может сделать final-merge;
- findings reviewer/QA действительно влияют на рабочий процесс;
- успешный final merge верифицируется состоянием Git.

### Flow B — Epic

Проследить:

```text
Epic
→ child Tasks
→ child task branches target epic branch
→ child integrations
→ INTEGRATED_INTO_EPIC
→ Epic Review / QA
→ final master integration
→ FINAL_MERGE approval
→ master
→ child Tasks RELEASED
```

Проверить, что семантика выпуска child Task точно соответствует дизайну.

### Flow C — Failed agent run

Проследить:

```text
Agent failure
→ Failure classification
→ Recovery policy
→ resume/retry/escalation
→ no-progress / loop detection
→ budget guard
→ user escalation when required
```

### Flow D — Crash during Git mutation

Проследить:

```text
GitOperation STARTED
→ process interruption
→ restart
→ startup reconciliation
→ inspect actual Git state
→ VERIFIED or GIT_STATE_DRIFT
```

Проверить, что повторы не создают дублирующие ветки/worktrees/merge.

### Flow E — Hermes autonomous task

Проследить реальный путь Plan 4:

```text
Run
→ scoped Hermes profile/session
→ Context Engine
→ Hermes process
→ MCP / Action Gateway
→ tool invocation
→ submit_result
→ Output Validator
→ domain state
```

Проверить, что E2E тест испытывает реальный путь, а не shortcut.

### Flow F — Planning/UI request

Проследить пользовательский путь Plan 5/6:

```text
Web UI request
→ Coordinator / Planning
→ Proposal / Plan
→ required approval
→ Epic/Tasks
→ execution
```

Если UI только отображает данные, но не может завершить предполагаемый рабочий процесс, классифицируйте это как пробел.

## Phase 3 — Аудит соответствия архитектуре

Сравнить реализацию с каждым основным инвариантом дизайна.

Как минимум проверить:

### Modular monolith boundaries

- модули владеют своим состоянием;
- нет произвольного доступа к таблицам между модулями, где был указан API/event boundary;
- команды, запросы и события семантически различны;
- обработчики событий идемпотентны, где требуется.

### Deterministic-first rule

Поискать вызовы LLM/runtime в:

- планировании;
- разрешениях;
- состоянии Git/worktree;
- исполнении бюджета;
- миграциях;
- политике одобрения;
- механике повторов;
- переходах состояний.

Пометить любое использование, где детерминированный код должен владеть решением.

### Source-of-truth boundaries

Проверить:

- Git владеет кодом;
- SQLite владеет состоянием/историей оркестрации;
- файлы `.orchestrator` в репозитории владеют контролируемым репозиторием знанием/конфигурацией;
- секреты никогда не становятся содержимым репозитория или контекстом промпта.

### Runtime abstraction

Подтвердить, что основная логика предметной области зависит от абстракции `AgentRuntime`, а не от специфичных для Hermes классов.

### Role boundaries

Подтвердить, что Developer, Reviewer, QA и Integration не могут молча выполнять привилегированные действия друг друга.

## Phase 4 — Аудит безопасности

Выполнить ревизию с позиции атакующего.

### Action Gateway

Проверить, что все пути мутации, доступные агенту, проходят через Permission Engine.

Поискать прямые использования:

- API мутации файловой системы;
- `child_process`;
- выполнения процесса Git;
- выполнения shell;
- GitHub credentials/API мутации;
- команд merge;
- мутации конфигурации проекта.

Любой обход, доступный из выполняемого агентом кода, — критическое обнаружение.

### Path containment

Протестировать:

- escape `../`;
- absolute вне пути;
- Windows junction escape;
- Unix symlink escape, где доступно;
- path-prefix confusion;
- не существующий child ниже symlinked ancestor.

### Process execution

Проверить:

- `shell:false` для обычного выполнения команд;
- интерпретаторы shell — отдельные привилегированные действия;
- ограниченный stdout/stderr;
- timeout и cancellation;
- allowlist дочерней среды;
- нет случайной утечки секрета/SSH агента.

### Git

Проверить:

- управляемые операции по умолчанию не выполняют репозиторийные hooks;
- нет неявного сетевого доступа во время reconciliation;
- нет Developer push/final merge;
- точная проверка темы/типа/статуса одобрения;
- нет инъекции команд через input ветки/ref/пути.

### Prompt injection / untrusted repo content

Подтвердить:

- текст репозитория — данные, а не авторитет;
- инструкции репозитория не могут изменять разрешения;
- неизвестная конфигурация `.orchestrator` не доверяется автоматически;
- MCP/plugin/config файлы из управляемых репозиториев не авторизуются автоматически.

### Local backend

Проверить:

- loopback binding;
- модель сессии/авторизации;
- CSRF/origin protections;
- нет секрета в API responses/логах.

Создать регрессионные тесты для каждого подтверждённого дефекта.

## Phase 5 — Аудит персистентности, миграций и восстановления

Проверить:

- каждая миграция имеет детерминированную упорядоченность/версионирование;
- применение миграции транзакционно, где возможно;
- бэкап создаётся перед апгрейдом схемы, если это требуется дизайном;
- внешние ключи включены;
- WAL/ожидаемые конфигурации применены;
- мутация outbox атомарна с состоянием предметной области;
- доставка job/event идемпотентна;
- существует dead-letter поведение;
- старт остаётся в RECOVERING до завершения reconciliation;
- Scheduler не делает dispatch до завершения восстановления;
- работает single-instance lock/lease поведение;
- устаревшие leases восстанавливаются;
- crash failpoints покрыты тестами.

Поискать предположения о схеме, не представленные миграциями.

Создать новую пустую базу данных и запустить все миграции с нуля.

Также мигрировать представительскую схему до текущей, если существуют fixtures миграций.

## Phase 6 — Аудит Scheduler, конкуррентности и бюджета

Проверить:

- зависимости блокируют правильно;
- resource locks предотвращают конфликтную работу;
- лимиты конкуррентности проекта/globale/роли enforced;
- приоритет и fairness/aging работают;
- нет preemption активных run, если явно не предусмотрено;
- каждая blocked/waiting задача имеет объяснимую причину;
- резервация бюджета происходит перед dispatch;
- параллельные резервации не могут перерасходовать из-за гонок;
- soft limit → ASK;
- hard limit → DENY;
- затраты на восстановление/переделку атрибутируемы;
- неизвестное ценообразование модели не становится молча бесплатным использованием;
- фактическое использование reconciles с резервацией.

Добавить тесты конкуррентности для путей, чувствительных к гонкам.

## Phase 7 — Аудит Context, Role contract и Hermes

Проверить:

- стабильные/версионированные RoleContracts;
- правильные роли доступны на текущей стадии v1;
- выходные схемы соответствуют фактическому поведению валидатора;
- AI не может придумать persistent ID;
- `submit_result` — авторитетный;
- попытки ремонта невалидного вывода ограничены;
- стабильные Finding/Defect ID выживают при повторном ревью;
- scope контекста минимален;
- исходный код загружается по требованию;
- ContextDelta существует, когда меняется авторитетный контекст;
- нет вечной сессии Coordinator на весь проект;
- изоляция Hermes session/profile работает для параллельных запусков;
- профили/конфигурации не перезаписывают друг друга;
- MCP tools связаны с capabilities;
- прямой Hermes global memory/delegation отключен/ограничен по дизайну.

Проверить, что парсинг stdout не случайно трактуется как авторитетный, когда существует `submit_result`.

## Phase 8 — Аудит Git/worktree/integration

Используя временные репозитории, проверить:

- Task worktree начинается от текущего target;
- Epic child нацелен на epic branch;
- standalone task нацелен на master;
- integration использует отдельный worktree/ветку;
- merge target merged в feature, а не destructive rebase;
- conflict records сохраняют информацию о конфликте первого класса;
- ручной внешний Git drift обнаруживается;
- failed/cancelled worktrees сохраняются согласно политике;
- cleanup никогда не уничтожает неподтверждённые данные пользователя;
- retry/reconciliation идемпотентен.

Запустить тесты с именами веток, именами файлов и путями репозитория, содержащими пробелы и shell metacharacters.

## Phase 10 — Аудит интеграции с GitHub

Проверить:

- GitHub опционален;
- локальный рабочий процесс продолжается, когда GitHub недоступен;
- внешние операции становятся `SYNC_PENDING` вместо блокировки основной работы;
- credentials никогда не exposed в Hermes;
- sync идемпотентен;
- предотвращено дублирование создания PR/issue;
- polling/manual sync state устойчив;
- GitHub failures retriable;
- remote данные никогда не перезаписывают молча авторитетное локальное состояние без reconciliation.

Не требовать подключения GitHub для детерминированного CI.

Поискать:

- `any`;

- широкие eslint disables;
- non-null assertions;

- дублирующаяся логика предметной области;

- TODO/FIXME/HACK;

- ad hoc JSON парсинг без схем.

Не выполнять косметические рефакторы только ради стиля.

Рефакторить только когда есть конкретная выгода для поддерживаемости, корректности, безопасности или тестируемости.

## Phase 12 — Аудит качества набора тестов

Не судить о качестве тестов по количеству прохождений.

Проверить:

- существуют содержательные утверждения;
- тесты не просто утверждают детали реализации;
- не прошедшие тесты не были отключены/пропущены;
- ни один важный набор тестов не был удалён во время предыдущих ремонтов;
- E2E тесты испытывают реальное подключение;
- test fixtures соответствуют текущим API;
- race/recovery/security инварианты имеют покрытие;
- тесты ожидаемого сбоя действительно падают до фикса;
- пробелы в покрытии существуют только в low-risk glue code.

Поискать:

```text
.skip
.todo
only(
it.only
test.only
describe.only
```

Любой намеренно пропущенный тест должен иметь явно задокументированную причину.

Добавить недостающие тесты с высокой ценностью для регрессии.

---

## Phase 13 — Аудит сборки/пакета/воспроизводимости

Проверить из чистого checkout/worktree:

```bash
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
```

Также проверить production builds для каждого пакета/приложения, имеющего этап сборки.

Проверить:

- `packageManager` соответствует желаемой версии pnpm;
- lockfile согласован;
- workspace зависимости явные;
- нет недекларированной зависимости от hoisted пакетов;
- сгенерированный JS не emission рядом с TS исходником;
- `*.tsbuildinfo`/сборочные артефакты правильно игнорируются;
- сгенерированные артефакты не загрязняют репозиторий после обычной проверки.

---

## Phase 14 — Аудит документации и операционной деятельности

Проверить, что документация отражает фактическое поведение для:

- локальная установка;
- версия pnpm;
- поддерживаемая версия Node;
- старт;
- онбординг проекта;
- prerequisites/config Hermes;
- ограничения безопасности Local Mode;
- опциональная интеграция GitHub;
- backup/recovery;
- troubleshooting;
- directory layout;
- приоритеты конфигурации;
- секреты;
- процесс upgrade/migration.

Не документировать будущие функции как существующие.

---

## Phase 15 — Классификация обнаружений

Создать структурированный отчёт аудита.

Каждое обнаружение должно содержать:

```text
ID
Severity: BLOCKER | HIGH | MEDIUM | LOW
Category
Affected requirement/spec section
Evidence
Root cause
Impact
Recommended action
Auto-fixable: yes/no
Requires architecture/scope approval: yes/no
Regression test required: yes/no
Status
```

Руководство по Severity:

### BLOCKER

Примеры:

- потеря данных;
- обход привилегии/gраницы безопасности;
- duplicate/unsafe merge;
- необратимая corruption Git;
- обход final approval;
- основной рабочий процесс не может завершиться;
- миграция портит состояние;
- секреты exposed.

### HIGH

Примеры:

- основной утверждённый рабочий процесс отсутствует/не подключен;
- crash recovery ненадёжен;
- бюджет/политика безопасности не enforced;
- false success/completion состояния;
- некорректный Epic/Task lifecycle.

### MEDIUM

Примеры:

- слабая обработка ошибок;
- неполное покрытие edge cases;
- дефект поддерживаемости, вероятно, приводящий к будущим багам;
- UI workflow неполон, но бэкенд безопасен.

### LOW

Примеры:

- локальная чистка;
- несоответствие документации;
- незначительное дублирование без влияния на корректность.

---

## Phase 16 — Политика автономного устранения недостатков

После создания начального инвентаря обнаружений:

### Автоматически исправить

Реализовать findings BLOCKER/HIGH/MEDIUM, когда все истинны:

- утверждённая спецификация уже определяет правильное поведение;
- не нужно решение о продукте/архитектуре;
- изменение остаётся в пределах v1 scope;
- не нужно предпочтение пользователя;
- регрессионный тест может доказать исправление.

Также исправить findings LOW, когда они тривиальны и low-risk.

### Не реализовывать молча

Создать предложение, когда исправление бы:

- изменило утверждённую архитектуру;
- добавило новую подсистему/провайдера;
- изменило видимую для пользователя семантику продукта, не указанную сегодня;
- изменило ответственность ролей;
- изменило требования одобрения;
- ослабило или существенно переделало политику безопасности;
- заменило технологию персистентности/хранения;
- существенно расширило v1 scope;
- потребовало бы крупного миграции зависимостей/фреймворка.

Поместите такие предложения в финальный отчёт под:

```text
REQUIRES HUMAN DECISION
```

Не блокируйте неподходящие безопасные ремонты.

---

## Phase 17 — Цикл устранения недостатков

Для каждого auto-fixable обнаружения:

1. Напишите/идентифицируйте падающий регрессионный тест.
2. Проверьте, что он падает по ожидаемой причине.
3. Реализуйте минимальное исправление корневой причины.
4. Запустите сфокусированные тесты.
5. Запустите релевантный typecheck/lint.
6. Проверьте diff.
7. Сделайте сфокусированный коммит исправления.

Рекомендуемые префиксы коммитов:

```text
fix:
test:
refactor:
docs:
security:
```

Не объединяйте неподходящие обнаружения в один гигантский коммит.

После каждого логического батча запустите:

```bash
pnpm lint
pnpm typecheck
pnpm test
```

Если ремонт вызывает новый сбой, исследуйте корневую причину, а не наслаивайте подавления.

---

## Phase 18 — Независимый финальный ревью

После устранения недостатков запустите свежий независимый reviewer, который не реализовывал исправления.

Попросите его просмотреть полную ветку против:

- утверждённого дизайна;
- планов 1–6;
- результатов аудита;
- модели безопасности;
- финального diff против `master`.

Reviewer должен специально искать:

- ослабление тестов;
- скрытое расширение scope;
- обходы разрешений;
- архитектуруные отклонения;
- небезопасное поведение Git;
- недостающие миграции;
- race conditions;
- fake E2E подключение;
- dead/неполные реализации;
- случайное exposed секрета/сети.

Все findings BLOCKER/HIGH reviewer должны быть исправлены.

Findings MEDIUM должны быть исправлены, если они не требуют утверждённого решения об архитектуре.

Запустите второй проход ревью после корректировок с нагрузкой.

---

## Phase 19 — Финальная верификация всей системы

Запустите из финальной ветки аудита:

```bash
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
git diff --check
git status --short
```

Запустите все явные E2E/scenario/security/recovery suites, если они отделены от команды тестов по умолчанию.

Создайте совершенно новую временную Orchestrator home/базу данных и проверьте:

```text
STARTING
→ migrations
→ RECOVERING
→ reconciliation
→ READY
```

Запустите хотя бы:

1. standalone Task happy path;
2. Epic happy path;
3. approval denied path;
4. Developer forbidden-action path;
5. failed run + retry/recovery path;
6. crash/reconciliation path;
7. budget soft-limit path;
8. budget hard-limit path;
9. path escape denial;
10. Git hook suppression;
11. Hermes autonomous Task E2E;
12. local operation, когда GitHub недоступен.

Если существуют автоматизированные тесты Web UI, запустите их.

Если существует browser E2E, запустите его.

## Phase 20 — Отчёт о готовности к релизу

Создать:

### Executive summary

- общий статус реализации;
- соответствует ли v1 утверждённому дизайну;
- готов ли к локальному релизу v1;
- остающиеся известные ограничения.

### Verification results

Точные результаты для:

```text
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
git diff --check
git status --short
```

### Findings

Сгруппировать:

```text
FIXED
ACCEPTED LIMITATIONS
REQUIRES HUMAN DECISION
```

### Architecture coverage

Для каждого основного раздела дизайна указать:

```text
PASS
PARTIAL
FAIL
```

с доказательствами.

Не помечать PASS только на основе присутствия файлов.

### Security summary

Явно сообщить:

- review обхода Action Gateway;
- path containment;
- shell/process policy;
- Git hooks;
- секреты;
- enforcement одобрения;
- граница prompt-injection;
- ограничения local-mode.

### Reliability summary

Явно сообщить:

- startup recovery;
- Git journal/reconciliation;
- идемпотентность;
- конкуррентность;
- Scheduler;
- резервация бюджета;
- миграции/бэкапы.

### Test summary

Сообщить фактические количества тестов и покрытие notable сценариев.

### Git summary

Сообщить:

```bash
git log --oneline master..HEAD
git diff --stat master...HEAD
git status --short
```

### Финальные категории рекомендаций

Использовать только эти статусы готовности:

```text
READY_FOR_V1_INTEGRATION
READY_WITH_DOCUMENTED_LIMITATIONS
NOT_READY
```

Этот статус о готовности релиза ПО, а не о ценности продукта/бизнеса.

## Финальные ворота завершения

Аудит завершён только когда:

- каждый BLOCKER исправлен;
- каждый HIGH исправлен, если он не требует явного решения об архитектуре/объёме;
- все auto-fixable MEDIUM обнаружения решены;
- независимый финальный ревью не имеет unresolved load-bearing обнаружений;
- полный детерминированный набор тестов прошёл;
- все требуемые E2E/security/recovery сценарии прошли;
- typecheck прошёл;
- lint прошёл;
- `git diff --check` прошёл;
- working tree чиста;
- остающиеся ограничения/предложения явно задокументированы.

Не мержить в `master`.

Не пушить.

Не начинать интеграцию OpenSpec или любую работу над функциональностью после v1.

Остановиться с отчётом о готовности к релизу и ждать, пока пользователь решит, как интегрировать ветку аудита.
