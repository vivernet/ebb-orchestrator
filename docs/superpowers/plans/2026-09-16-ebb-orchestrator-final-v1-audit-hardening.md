# Ebb AI Development Orchestrator — Final V1 Audit & Hardening Plan

> **Для агентов-работников:** ОБЯЗАТЕЛЬНЫЙ ПОДСКЛЮ: Используйте `superpowers:subagent-driven-development`, где полезны независимые проверки. Этот план является планом аудита и устранения, а не обычным планом реализации функции. Не объявляйте завершение, пока не пройдены все финальные ворота в этом документе.

**Цель:** Провести полный аудит проекта Ebb AI Development Orchestrator после слияния Планов 1–6, выявить пробелы реализации против утверждённого дизайна и канонических планов, устранить дефекты в рамках утверждённой архитектуры и оставить репозиторий в состоянии, готовом к релизу, и полностью верифицированном.

**Архитектура:** Аудит рассматривает утверждённую спецификацию дизайна и канонические Планы 1–6 как авторитет. Он сначала строит инвентарь реализации, основанный на доказательствах, затем проверяет архитектуру, инварианты предметной области, безопасность, поведение Git/worktree, интеграцию с Hermes runtime, персистентность/восстановление, UI/API, интеграцию с GitHub, тесты, миграции, конкурентность, бюджеты, конфигурацию и операционное качество. Находки, которые могут быть исправлены без изменения утверждённой архитектуры, исправляются автономно; изменения архитектуры/объёма преобразуются в явные предложения и не реализуются неявно.

**Стек технологий:** TypeScript, Node.js, pnpm, Fastify, React/Vite, Vitest, SQLite, Git worktrees, Hermes runtime, GitHub adapter.

## Глобальные ограничения

- Все ответы, ориентированные на пользователя, обновления прогресса, выводы аудита, объяснения, заключения, отчёты и видимая рассуждения должны быть написаны на русском языке.
- Сохраняйте идентификаторы исходного кода, пути к файлам, команды, имена API, имена схем/свойств, Git-ссылки, сообщения об ошибках и канонические технические термины без изменений, если их перевод снизил бы точность.
- При цитировании существующей английской документации или комментариев к коду сохраняйте оригинальный текст, когда точная формулировка имеет значение, но объясните его смысл на русском.
- Работайте только в выделенной ветке/worktree аудита, созданной из текущего чистого `master`.
- Не проводите аудит напрямую на `master`.
- Не делайте push, не открывайте PR, не сливайте, не делайте rebase/reset/force-clean и не удаляйте worktrees без явного указания после завершения аудита.
- Не изменяйте неявно утверждённую архитектуру, предметную область, модель ролей, модель безопасности, семантику рабочего процесса или модель персистентности.
- Исправляйте дефекты, отсутствующие соединения, неполные тесты, плохую типизацию, мёртвый код, дублирование, небезопасное поведение и проблемы качества, которые явно нарушают или не удовлетворяют утверждённый дизайн.
- Если предлагаемое исправление существенно меняет архитектуру, поведение продукта, семантику рабочего процесса, политику безопасности или область, создайте предложение вместо его реализации.
- Deterministic-first остаётся обязательным: если обычный код может надёжно принять решение, не добавляйте зависимость от LLM.
- `master` является канонической веткой по умолчанию для этого репозитория, если конфигурация проекта явно не переопределяет это для управляемого внешнего проекта.
- Не ослабляйте ESLint, строгость TypeScript, тесты, границы безопасности или правила утверждения лишь для прохождения контрольных точек качества.
- Не решайте ошибки типов с помощью широких `any`, небезопасных приведений или утверждений non-null, если инвариант явно не доказан.
- Не удаляйте тесты только потому, что они падают.
- Не добавляйте совместимостные обёртки только для того, чтобы скрыть устаревшие импорты, когда канонический API может быть исправлен.
- Каждое исправление должно иметь регрессионный тест, если изменение только документационное или чистое удаление мёртвого кода с существующим покрытием.
- Предпочитайте небольшие сфокусированные коммиты, сгруппированные по корневой причине.
- Финальное завершение требует чистого рабочего дерева.


## Phase 2 — Trace critical end-to-end flows

Проверить эти потоки, читая код и запуская тесты.

### Flow A — Standalone Task

Проследить:

```text
Request
→ Task
→ scheduler eligibility
→ runtime dispatch
→ Developer
→ Reviewer
→ QA
→ Integration
→ FINAL_MERGE approval
→ deterministic MergeService
→ RELEASED
```

Проверить:

- правильные переходы состояний;
- утверждения на правильных границах;
- отсутствие прямого AI-изменения состояния предметной области;
- правильную принадлежность worktree/branch;
- Developer не может делать final-merge;
- находки reviewer/QA действительно влияют на рабочий процесс;
- успешное final merge верифицировано Git state.

### Flow B — Epic

Проследить:

```text
Epic
→ child Tasks
→ child task branches target epic branch
→ child integrations
→ INTEGRATED_INTO_EPIC
→ Epic Review / QA
→ final current-master integration
→ FINAL_MERGE approval
→ master
→ child Tasks RELEASED
```

Проверить, что семантика выпуска child Task точно соответствует дизайну.

### Flow C — Failed agent run

Проследить:

```text
Agent failure
→ Failure classification
→ Recovery policy
→ resume/retry/escalation
→ no-progress / loop detection
→ budget guard
→ user escalation when required
```

### Flow D — Crash during Git mutation

Проследить:

```text
GitOperation STARTED
→ process interruption
→ restart
→ startup reconciliation
→ inspect actual Git state
→ VERIFIED or GIT_STATE_DRIFT
```

Обеспечить, что повторные попытки не создают дублирующие ветки/worktrees/слияния.

### Flow E — Hermes autonomous task

Проследить реальный путь Plan 4:

```text
Run
→ scoped Hermes profile/session
→ Context Engine
→ Hermes process
→ MCP / Action Gateway
→ tool invocation
→ submit_result
→ Output Validator
→ domain state
```

Проверить, что E2E тест исследует реальный путь, а не сокращение.

### Flow F — Planning/UI request

Проследить пользовательский путь Plan 5/6:

```text
Web UI request
→ Coordinator / Planning
→ Proposal / Plan
→ required approval
→ Epic/Tasks
→ execution
```

Если UI только рендерит данные, но не может завершить предназначенный рабочий процесс, классифицируйте это как пробел.

## Phase 3 — Architecture conformance audit

Сравнить реализацию с каждым ключевым инвариантом дизайна.

Минимум проверить:

### Modular monolith boundaries

- модули владеют своим состоянием;
- отсутствует произвольный доступ к таблицам между модулями, где была указана граница API/event;
- команды, запросы и события остаются семантически различными;
- обработчики событий идемпотентны, где требуется.

### Deterministic-first rule

Поискать вызовы LLM/runtime в:

- планировании;
- разрешениях;
- Git/worktree state;
- принудительном применении бюджета;
- миграциях;
- политике утверждения;
- механике повторных попыток;
- переходах состояний.

Отметить любое использование, где детерминированный код должен владеть решением.

### Source-of-truth boundaries

Проверить:

- Git владеет кодом;
- SQLite владеет состоянием/историей оркестрации;
- файлы `.orchestrator` репозитория владеют знаниями/конфигурацией, контролируемыми репозиторием;
- секреты никогда не становятся содержимым репозитория или контекстом промпта.

### Runtime abstraction

Подтвердить, что ключевая логика предметной области зависит от абстракции `AgentRuntime`, а не от специфичных для Hermes классов.

### Role boundaries

Подтвердить, что Developer, Reviewer, QA и Integration не могут неявно выполнять привилегированные действия друг друга.

## Phase 4 — Security audit

Провести враждебный обзор.

### Action Gateway

Проверить, что все пути изменения, ориентированные на агентов, проходят через Permission Engine.

Поискать прямые использования:

- API изменения файловой системы;
- `child_process`;
- выполнение процесса Git;
- выполнение shell;
- GitHub credentials/API mutation;
- команды слияния;
- изменение конфигурации проекта.

Любое обходное решение, доступное из выполняемого под контролем агента, является критической находкой.

### Path containment

Протестировать:

- escape через `../`;
- абсолютный внешний путь;
- Windows junction escape;
- Unix symlink escape, где доступно;
- путаница с префиксом пути;
- несуществующий потомок ниже символически связанного предка.

### Process execution

Проверить:

- `shell:false` для обычного выполнения команд;
- интерпретаторы shell являются отдельными привилегированными действиями;
- ограниченные stdout/stderr;
- timeout и отмена;
- allowlist окружения дочернего процесса;
- отсутствие случайной утечки секрета/SSH agent.

### Git

Проверить:

- управляемые операции по умолчанию не выполняют хуки репозитория;
- нет неявного сетевого доступа во время reconciliation;
- нет push/final merge для Developer;
- точная проверка субъекта/типа/статуса утверждения;
- нет injection команд через ввод branch/ref/path.

### Prompt injection / untrusted repo content

Подтвердить:

- текст репозитория — это данные, а не авторитет;
- инструкции репозитория не могут изменять разрешения;
- неизвестная конфигурация `.orchestrator` не доверяется автоматически;
- MCP/plugin/config файлы из управляемых репозиториев не авторизуются автоматически.

### Local backend

Проверить:

- привязка к loopback;
- модель session/auth;
- защиты CSRF/origin;
- нет секрета в ответах API/логах.

Создать регрессионные тесты для каждой подтверждённой находки.

## Phase 5 — Persistence, migrations and recovery audit

Проверить:

- каждая миграция имеет детерминированный порядок/версионирование;
- применение миграции является транзакционным, где возможно;
- резервная копия создаётся перед обновлениями схемы, если требуется дизайном;
- внешние ключи включены;
- применяются ожидания WAL/config;
- изменение outbox state атомарно с domain state;
- доставка job/event идемпотентна;
- существует поведение dead-letter;
- запуск остаётся RECOVERING до завершения reconciliation;
- scheduler не диспетчирует до завершения восстановления;
- работает поведение single-instance lock/lease;
- устаревшие leases восстанавливаются;
- точки сбоя при краше покрыты тестами.

Поискать предположения о схеме, не представленные миграциями.

Создать новую пустую базу данных и запустить все миграции с нуля.

Также выполните миграцию репрезентативной предыдущей схемы, если существуют fixtures миграций.

## Phase 6 — Scheduler, concurrency and budget audit

Проверить:

- зависимости блокируют правильно;
- блокировки ресурсов предотвращают конфликтную работу;
- применяются лимиты конкурентности проекта/global/role;
- работают приоритет и справедливость/старение;
- нет преэмпции активных запусков, если явно не предусмотрено;
- каждая заблокированная/ожидающая задача имеет объяснимую причину;
- резервирование бюджета происходит до диспетчеризации;
- параллельные резервирования не могут перерасходовать из-за гонок;
- soft limit → ASK;
- hard limit → DENY;
- расход recovery/rework атрибутируется;
- неизвестное ценообразование моделей не становится автоматически бесплатным использованием;
- фактическое использование согласуется с резервированием.

Добавить тесты конкурентности для путей, чувствительных к гонкам.

## Phase 7 — Context, role contract and Hermes audit

Проверить:

- стабильные/версионированные RoleContracts;
- правильные роли доступны на текущем этапе v1;
- output schemas соответствуют фактическому поведению валидатора;
- AI не может придумывать постоянные ID;
- `submit_result` является авторитетным;
- попытки ремонта невалидного output ограничены;
- стабильные Finding/Defect IDs выживают при повторном обзоре;
- scope контекста минимален;
- исходный код загружается по требованию;
- ContextDelta существует, когда авторитетный контекст меняется;
- нет вечной сессии Coordinator на весь проект;
- изоляция Hermes session/profile работает для параллельных запусков;
- профили/конфигурации не перезаписывают друг друга;
- MCP инструменты связаны с возможностями;
- прямой доступ к глобальной памяти/delegation Hermes отключен/ограничен как предусмотрено.

Проверить, что парсинг stdout не случайным образом считается авторитетным, когда существует `submit_result`.

## Phase 8 — Git/worktree/integration audit

Используя временные репозитории, проверить:

- Task worktree начинается от текущего target;
- Epic child целится в epic branch;
- standalone task целится в master;
- integration использует отдельный worktree/branch;
- merge target сливается в feature, а не деструктивный rebase;
- записи конфликтов сохраняют информацию о конфликте первого уровня;
- обнаруживается внешний Git drift;
- failed/cancelled worktrees сохраняются согласно политике;
- очистка не уничтожает неподтверждённые данные пользователя;
- retry/reconciliation идемпотентны.

Запустить тесты с именами веток, именами файлов и путями репозитория, содержащими пробелы и спецсимволы shell.

## Phase 10 — GitHub integration audit

Проверить:

- GitHub опционален;
- локальный рабочий процесс продолжается, когда GitHub недоступен;
- внешние операции становятся `SYNC_PENDING` вместо блокирования основной работы;
- credentials никогда не передаются Hermes;
- синхронизация идемпотентна;
- предотвращено создание дублирующих PR/issue;
- состояние polling/manual sync долговечно;
- сбои GitHub могут быть повторены;
- удалённые данные никогда не перезаписывают авторитетный локальный state без reconciliation.

Не требовать подключения GitHub для детерминированного CI.

## Phase 12 — Test suite quality audit

Не оценивать качество тестов по количеству прохождений.

Проверить:

- существуют значимые утверждения;
- тесты не просто утверждают детали реализации;
- неудавшиеся тесты не были отключены/пропущены;
- ни один важный набор не был удалён во время предыдущих ремонтов;
- E2E тесты исследуют реальное подключение;
- тестовые fixtures соответствуют текущим API;
- инварианты race/recovery/security имеют покрытие;
- ожидаемые тесты на провал фактически падают до исправления;
- пробелы покрытия существуют только в низко-рисковом glue code.

Поискать:

```text
.skip
.todo
only(
it.only
test.only
describe.only
```

Любой намеренно пропущенный тест должен иметь явно задокументированную причину.

Добавить недостающие тесты регрессии высокой ценности.

---

## Phase 13 — Build/package/reproducibility audit

Проверить с чистого checkout/worktree:

```bash
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
```

Также проверить production builds для каждого пакета/приложения, имеющего шаг сборки.

Проверить:

- `packageManager` соответствует предполагаемой версии pnpm;
- lockfile консистентен;
- зависимости workspace явны;
- нет недекларированной зависимости от поднятых пакетов;
- сгенерированный JS не эмитируется рядом с исходным TS;
- `*.tsbuildinfo`/сборочные артефакты правильно игнорируются;
- сгенерированные артефакты не загрязняют репозиторий после нормальной проверки.

## Phase 14 — Documentation and operational audit

Проверить, что документация отражает текущее поведение для:

- локальной установки;
- версии pnpm;
- поддерживаемой версии Node;
- запуска;
- онбординга проекта;
- предварительных условий/конфигурации Hermes;
- ограничений безопасности Local Mode;
- опциональной интеграции GitHub;
- резервного копирования/восстановления;
- устранения неполадок;
- раскладки директорий;
- приоритета конфигурации;
- секретов;
- процесса обновления/миграции.

Не документировать будущие функции как существующие.

## Phase 15 — Findings classification

Создать структурированный отчёт аудита.

Каждая находка должна содержать:

```text
ID
Severity: BLOCKER | HIGH | MEDIUM | LOW
Category
Affected requirement/spec section
Evidence
Root cause
Impact
Recommended action
Auto-fixable: yes/no
Requires architecture/scope approval: yes/no
Regression test required: yes/no
Status
```

Рекомендации по Severity:

### BLOCKER

Примеры:

- потеря данных;
- обход привилегии/границы безопасности;
- дублирующееся/небезопасное слияние;
- необратимое повреждение Git;
- обход финального утверждения;
- основной рабочий процесс не может завершиться;
- миграция повреждает состояние;
- секреты раскрыты.

### HIGH

Примеры:

- важный одобренный рабочий процесс отсутствует/неподключен;
- восстановление после краша ненадёжно;
- политика бюджета/безопасности не применяется;
- ложные состояния успеха/завершения;
- неверный цикл жизни Epic/Task.

### MEDIUM

Примеры:

- слабая обработка ошибок;
- неполное покрытие краевых случаев;
- дефект поддерживаемости, вероятно, приводящий к будущим багам;
- неполный UI рабочий процесс, но бэкенд безопасен.

### LOW

Примеры:

- локальная очистка;
- несоответствие документации;
- незначительное дублирование без влияния на корректность.

## Phase 16 — Autonomous remediation policy

После создания начального инвентаря находок:

### Автоматически исправить

Реализовывать находки BLOCKER/HIGH/MEDIUM, когда все верно:

- утверждённая спецификация уже определяет правильное поведение;
- не нужно решения продукта/архитектуры;
- изменение остаётся в пределах v1 scope;
- не нужно предпочтений пользователя;
- регрессионный тест может доказать исправление.

Также исправлять находки LOW, когда они тривиальны и низко-рисковы.

### Не реализовывать неявно

Создавать предложение вместо, когда исправление бы:

- изменило утверждённую архитектуру;
- добавило новую подсистему/провайдера;
- изменило семантику видимого продукта пользователя, не указанную сегодня;
- изменило обязанности ролей;
- изменило требования утверждения;
- ослабило или существенно переосмыслило политику безопасности;
- заменило технологию персистентности/хранения;
- существенно расширило v1 scope;
- потребовало бы миграции главного зависимости/фреймворка.

Поместить такие предложения в финальный отчёт под:

```text
REQUIRES HUMAN DECISION
```

Не блокировать не связанные безопасные ремонты.

---

## Phase 17 — Remediation loop

Для каждой auto-fixable находки:

1. Написать/определить неудавшийся регрессионный тест.
2. Проверить, что он падает по ожидаемой причине.
3. Реализовать минимальное исправление корневой причины.
4. Запустить сфокусированные тесты.
5. Запустить relevant typecheck/lint.
6. Просмотреть diff.
7. Закоммитить сфокусированное исправление.

Рекомендуемые префиксы коммитов:

```text
fix:
test:
refactor:
docs:
security:
```

Не упаковывать не связанные находки в один огромный коммит.

После каждой логической группы запустить:

```bash
pnpm lint
pnpm typecheck
pnpm test
```

Если ремонт вызывает новый провал, исследуйте корневую причину вместо наложения подавлений.

---

## Phase 18 — Independent final review

После восстановления, запустить свежего независимого обзорщика, который не реализовывал исправления.

Попросить его просмотреть полную ветку против:

- утверждённого дизайна;
- Планов 1–6;
- находок аудита;
- модели безопасности;
- финального diff против `master`.

Обзорщик должен специально искать:

- ослабление тестов;
- скрытое расширение области;
- обходы разрешений;
- дрейф архитектуры;
- небезопасное поведение Git;
- отсутствующие миграции;
- race conditions;
- fake E2E подключение;
- мёртвые/неполные реализации;
- случайное раскрытие секрета/сети.

Все находки обзорщика BLOCKER/HIGH должны быть исправлены.

Находки MEDIUM должны быть исправлены, если они не требуют утверждённого решения архитектуры.

Запустить второй проход обзора после нагрузочных исправлений.

## Phase 19 — Final full-system verification

Запустить из финальной ветки аудита:

```bash
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
git diff --check
git status --short
```

Запустить все явные E2E/scenario/security/recovery suites, если они отделены от команды тестирования по умолчанию.

Создать полностью новую временную домашнюю директорию/базу данных Orchestrator и проверить:

```text
STARTING
→ migrations
→ RECOVERING
→ reconciliation
→ READY
```

Запустить хотя бы:

1. standalone Task happy path;
2. Epic happy path;
3. approval denied path;
4. Developer forbidden-action path;
5. failed run + retry/recovery path;
6. crash/reconciliation path;
7. budget soft-limit path;
8. budget hard-limit path;
9. path escape denial;
10. Git hook suppression;
11. Hermes autonomous Task E2E;
12. local operation while GitHub is unavailable.

Если существуют автоматизированные тесты Web UI, запустите их.

Если существует browser E2E, запустите его.

```text
pnpm install --frozen-lockfile
```

Разделить на:

## Final completion gate

Аудит завершён только когда:

- каждая находка BLOCKER исправлена;
- каждая HIGH исправлена, если она не требует явного решения архитектуры/объёма;
- все auto-fixable MEDIUM находки разрешены;
- независимый финальный обзор не имеет нерешённых находок с нагрузкой;
- полный детерминированный набор тестов проходит;
- все требуемые E2E/security/recovery сценарии проходят;
- typecheck проходит;
- lint проходит;
- `git diff --check` проходит;
- рабочее дерево чистое;
- оставшиеся ограничения/предложения явно задокументированы.

Не делать слияние в `master`.

Не делать push.

Не начинать интеграцию OpenSpec или любую работу над функциями post-v1.

Остановиться с отчётом о готовности к релизу и дождаться решения пользователя о том, как интегрировать ветку аудита.
