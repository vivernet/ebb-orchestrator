# Ebb Orchestrator — переход на русский JSDoc и документацию README

> **Для агентов:** ОБЯЗАТЕЛЬНО использовать `superpowers:subagent-driven-development`. Для независимых непересекающихся модулей допускается `superpowers:dispatching-parallel-agents`. Каждый субагент получает эксклюзивный набор файлов. Финальную проверку выполняет отдельный агент, который не писал документацию.

**Цель:** После завершения Plans 1–6 и Final V1 Audit & Hardening привести весь собственный код Ebb Orchestrator к единому стандарту русскоязычного JSDoc, закрепить этот стандарт через `eslint-plugin-jsdoc` и полностью переписать корневой `README.md` как полноценную техническую документацию проекта.

**Архитектура:** Это этап только по документации. Он не меняет поведение приложения, публичные контракты, workflow, БД, модель безопасности или архитектуру. Работа выполняется в отдельном worktree; Coordinator сначала подключает lint-policy и строит карту файлов, затем раздаёт непересекающиеся области специализированным субагентам по документации. Отдельный субагент README переписывает только `README.md`. После этого независимый рецензент проверяет точность комментариев по реализации и спецификации, а финальный этап переводит правила JSDoc из режима миграции в обязательные ошибки.

**Технологический стек:** TypeScript, JavaScript, ESLint flat config, `eslint-plugin-jsdoc`, pnpm, Markdown.

**Основные источники истины:**
- `docs/superpowers/specs/2026-09-16-ebb-orchestrator-design.md`
- `docs/superpowers/plans/2026-09-16-ebb-orchestrator-v1-roadmap.md`
- канонические Plans 1–6;
- итоговый Final V1 Audit & Hardening report;
- текущий код после всех исправлений аудита.

- Запускать этот этап только после того, как Plans 1–6 и Final V1 Audit & Hardening интегрированы в `master`.
- Работать только в отдельной ветке/worktree, не на `master`.
- Все пользовательские ответы, промежуточные отчёты, найденные при проверке проблемы и финальный отчёт писать на русском языке.
- Все новые JSDoc-комментарии писать на грамотном русском языке.
- Имена классов, методов, API, полей, enum, Git refs, команды, пути, протоколы и другие технические идентификаторы не переводить.
- Не изменять поведение среды выполнения ради документации.
- Не переименовывать публичные API, классы, функции, типы или поля.
- Не менять сигнатуры, domain states, migrations, SQL, workflow transitions, security policy или permissions.
- Не выполнять несвязанный refactoring.
- Не исправлять найденные функциональные ошибки в рамках JSDoc-прохода. Зафиксировать их как проблему и продолжить документацию.
- Разрешены только минимальные технические изменения, необходимые непосредственно для lint/JSDoc-инфраструктуры и исправления комментариев.
- Не удалять существующие полезные комментарии без понимания их назначения.
- Не добавлять JSDoc, который просто дословно повторяет имя функции или TypeScript-сигнатуру.
- Не описывать поведение, которого нельзя доказать по коду, спецификации или тестам.
- Если назначение или инвариант неясны, оформить проблему вместо выдумывания объяснения.
- Не использовать AI-generated комментарии как источник истины: каждый комментарий должен быть проверен по реализации.
- Не документировать generated/vendor code как API собственного кода.
- Для тестов не требуется тотальный JSDoc; документировать только повторно используемые тестовые helpers/fixtures с действительно неочевидным контрактом.

- После финального коммита команда `git status --short` должна возвращать пустой результат.

# Стандарт русского JSDoc

## Что обязательно документировать

JSDoc обязателен для:

- экспортируемые классы;
- экспортируемые функции;
- экспортируемые React-компоненты/hooks;
- экспортируемые интерфейсы;
- экспортируемые псевдонимы типов, если они описывают доменный/публичный контракт;
- экспортируемые enums;
- публичных методов сервисов и адаптеров;
- методов/функций с важными побочными эффектами;
- кода, чувствительного к безопасности;
- Permission Engine / Action Gateway;
- Git/worktree/merge/reconciliation операций;
- логики workflow/переходов состояний;
- recovery/retry/loop-detection;
- budget/concurrency/resource-lock logic;
- операций сохранения с неочевидной границей транзакции;
- Hermes/runtime/context/MCP integration;
- функций с важными предусловиями/постусловиями;
- функций, которые намеренно выбрасывают значимые ошибки;
- сложных внутренних helpers, где без комментария трудно понять алгоритм или инвариант.

JSDoc обычно не требуется для:

- очевидных private getters/setters;
- trivial mappers;
- коротких локальных helpers с полностью самодокументируемым названием;
- простых переменных, используемых только в тесте;
- сгенерированных файлов;
- fixture data без reusable contract;
- импортов/экспортов;
- кода, где комментарий лишь перефразирует одну строку реализации.

## Что должен объяснять хороший комментарий

Приоритет:

1. назначение;
2. почему этот компонент существует;
3. важные invariants;
4. побочные эффекты;
5. границы доверия и безопасности;
6. предусловия;
7. ошибки;
8. неочевидный результат.

Комментарий не должен пересказывать TypeScript.

Плохо:

```ts
/**
 * Возвращает проект.
 *
 * @param id ID проекта.
 * @returns Проект.
 */
```

Хорошо:

```ts
/**
 * Загружает проект как текущий авторитетный контекст оркестрации.
 *
 * Метод не доверяет репозиторному `.orchestrator`-конфигу автоматически:
 * trust level проекта должен быть определён до использования локальных правил.
 *
 * @param id Идентификатор проекта в локальном состоянии Orchestrator.
 * @returns Текущая запись проекта с вычисленным trust level.
 * @throws {ProjectNotFoundError} Если проект отсутствует в локальном состоянии.
 */
```

## Правила тегов

- Не дублировать TypeScript-типы в `{Type}` внутри `@param`/`@returns`.
- Для публичного вызываемого API использовать `@param` для параметров, если их назначение не тривиально.
- `@returns` использовать, когда смысл результата требует пояснения.
- `@throws` указывать только для значимых документированных исключений.
- `@example` использовать только там, где пример действительно упрощает использование API.
- `@deprecated` использовать только для реально deprecated API.
- Не добавлять фиктивные `@returns`, `@throws` или `@example` ради прохождения lint.
- Описание тега должно быть полноценным русским объяснением, если тег присутствует.

## Особые требования по подсистемам

### Безопасность
Комментарий должен пояснять trust boundary, недоверенный ввод, смысл ALLOW/ASK/DENY/ABSOLUTE_DENY и проверки, которые нельзя обходить.

### Git
Комментарий должен пояснять целевой репозиторий/worktree, hooks, сетевые побочные эффекты, семантику журнала/reconciliation и постусловия.

### Workflow
Комментарий должен пояснять допустимый исходный state, target state, guards/approvals и сохраняемый invariant.

### Сохранение данных
Комментарий должен пояснять границу транзакции/idempotency, если она неочевидна.

### Hermes / среда выполнения агента
Комментарий должен отличать сессию в заданной области, профиль, контекст, capability, авторитетный структурированный результат и диагностический stdout/stderr.

# Задача 14 — Полная финальная проверка качества

Запустить:

```bash
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
git diff --check
```

Запустить все существующие команды сборки production.

Проверить:

```bash
git status --short
git diff --stat master...HEAD
git log --oneline master..HEAD
```

После всех коммитов команда `git status --short` должна возвращать пустой результат.

За исключением `eslint.config.js`, `package.json`, `pnpm-lock.yaml` и файлов документации изменения `src/**` должны быть только JSDoc/комментариями. Изменение runtime нужно вернуть или вынести в отдельный одобренный bugfix.

# Финальная проверка приёмки

Этап завершён только если:

- `eslint-plugin-jsdoc` установлен и закреплён в lockfile;
- постоянные правила JSDoc работают как errors;
- экспортируемый/публичный API собственного кода покрыт русским JSDoc;
- чувствительная к рискам внутренняя логика имеет полезную документацию;
- комментарии проверены по реализации;
- поведение runtime не изменено;
- `README.md` полностью переписан и соответствует текущему проекту;
- команды README проверены;
- независимая проверка документации завершена;
- `pnpm lint` PASS;
- `pnpm typecheck` PASS;
- `pnpm test` PASS;
- сборки production PASS;
- `git diff --check` PASS;
- рабочее дерево чистое;
- функциональные проблемы вынесены как findings, а не замаскированы документационными изменениями.
