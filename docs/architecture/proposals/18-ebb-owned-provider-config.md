# Proposal 18: Ebb-owned provider configuration for Orchestrator Runs

> **Amendment 2026-10-23 (plan-24, APPROVED):** Plan 24 расширяет этот proposal:
> Ebb-owned provider-конфигурация покрывает **полный каталог** провайдеров
> закреплённого LobeHub источника — все 86 provider ID — и управляется из Web.
> Credentials хранятся в OS `SecretStore` (keyring), а не в `.env`; SQLite
> хранит только opaque reference и несекретные настройки. Auth-lifecycle
> (API-ключи, subscription/coding-plan токены, OAuth device flow, refresh,
> disconnect) реализуется в Ebb (Tasks 2–6 плана 24). Hermes остаётся
> рантаймом по умолчанию (default selection). Пункты ниже, противоречащие
> этому amendment (read-only UI, ограничение двумя built-in провайдерами,
> `.env` как хранилище секретов, исключение OAuth/токен-флоу из v1),
> считаются superseded для реализации и сохранены как история.

## Решение (направление)

Пользователь принял решение (2026-10-23): **Ebb становится владельцем настройки ИИ-провайдеров и моделей** для Orchestrator Runs. Это заменяет Proposal 09 («Reuse the configured Hermes provider») для v1: Ebb хранит реестр провайдеров/моделей, а при запуске Run передаёт выбор в Hermes явными неинтерактивными средствами, не мутируя пользовательский профиль Hermes.

Хранение API-ключей — в **`.env`-файле** (по выбору пользователя; просто, секреты на диске вне БД/репозитория). Ключи не попадают в SQLite, логи, артефакты, UI.

## Почему это безопасно и реалистично

Read-only исследование установленного Hermes (2026-10-23) подтвердило:

- Hermes читает провайдера/модель из `config.yaml`, `.env`, процессных env-переменных и CLI-флагов `--provider <P> -m <M>`; `--oneshot` неявно включается без TTY; `--ignore-user-config` изолирует Run от пользовательского профиля (credentials из `.env` всё равно грузятся).
- Ключи API передаются документированными env-переменными (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, … или кастомные `key_env`). `.env` пользователя грузится с `override=True`, поэтому Ebb обязан выбирать имена переменных, отсутствующие в пользовательском `.env`, или использовать свои уникальные `key_env`.
- `hermes config get` маскирует credentials по умолчанию; `--raw` не использовать.
- `hermes model` / `hermes auth` интерактивны и для автоматизации непригодны.
- Адаптер Hermes в Ebb уже управляет запуском subprocess; добавление флагов выбора провайдера/модели и env-ключа не меняет port `AgentRuntime`.

## Контракт v1

1. **Ebb владеет провайдер-конфигурацией:** в `project`/server-конфигурации Ebb хранится реестр доступных провайдеров и моделей (без секретов): `{ id, providerName, model, keyEnv }` (секрет — только имя env-переменной, не значение). В v1 поддерживаются **только built-in провайдеры Hermes** (стандартные имена из registry + стандартные env-ключи). Пользовательские провайдеры (config-определённые/`key_env`) отложены до подтверждения механизма доведения до Hermes под `--ignore-user-config` в отдельном шаге.
2. **Секреты — только в `.env` Ebb:** файл — `EBB_ORCHESTRATOR_HOME/.env` (изолированно от репозитория; решение пользователя): только переменные `keyEnv` с API-ключами. Запрещено: запись ключей в SQLite/логи/артефакты/UI; чтение пользовательских `~/.hermes/.env`, `auth.json`, `config.yaml`.
3. **Запуск Run:** HermesRuntimeAdapter резолвит выбранного провайдера/модель для Run (из RunRequest/роли/настроек Ebb) и запускает `hermes chat … --provider <P> -m <M> --oneshot --ignore-user-config` (опции подкоманды `chat`) с env-переменной ключа (только для выбранного провайдера; стандартное имя env-переменной built-in провайдера). `--ignore-user-config` изолирует Run от пользовательского профиля; Ebb полагается на built-in провайдеры Hermes.
4. **UI (IN-005):** страницы Settings/Run получают read-only проекцию провайдеров/моделей Ebb (имена, статус доступности, выбранная модель для Run) без значений ключей; управление ключами — вне UI (редактирование `.env` вручную), либо, опционально, защищённая серверная форма, записывающая только в `.env` (решение по объёму — в плане).
5. **Совместимость:** `model=default` продолжает работать (использует провайдера/модель по умолчанию из реестра Ebb); отмена `HERMES_MODEL_OVERRIDE_UNSUPPORTED` — Ebb теперь может легитимно передавать явный выбор. Существующие Runs с `model='default'` не ломаются.
6. **Ограничения безопасности:**
   - не логировать и не отображать значения ключей;
   - не использовать `--raw`, `hermes model`, `hermes auth` в автоматизации;
   - выбирать имена env-переменных, отсутствующие в пользовательском `.env` (для built-in стандартные имена могут присутствовать — порядок приоритета child-env vs пользовательский `.env` фиксируется в F5-spike и acceptance-критерии; предотвращать затенение ключа);
   - `.env` Ebb — вне git (проверить/дополнить `.gitignore`), права файла ограничены;
   - не читать/не копировать пользовательские Hermes secrets.

## Что меняется

- **spec-01 §13.1** (~стр. 965–979): текст о «Ebb не требует provider/key mapping, не читает/не копирует credentials, не внедряет provider credential» переформулируется: Ebb управляет выбором провайдера/модели и хранит ключи в собственном `.env`; обязательства по не-чтению чужого Hermes credential store сохраняются.
- **spec-01 §10.2** (стр. 696–706): manifest/fingerprint — включить запись выбранного провайдера/модели (имена, не секреты) в контекстный fingerprint с версионированием Context Builder (F4); старые манифесты остаются валидными (dual-version decode).
- **Proposal 09**: помечается `superseded` proposal-18 (решение пользователя). Запись в `09-hermes-provider-auth-reuse.md` — историческая.
- **Plan20**: обновить контракты/принятые решения (модель больше не «только default»; разрешён явный выбор через Ebb-реестр; env-передача ключей).
- **Plan22**: Impact минимален (provider-errors/events не меняются; OTel/tracing остаются без provider-lab по значениям; допускаются имена провайдеров в метаданных? — нет, только имена, без URL/ключей).

## Не входит в v1

- Интерактивный OAuth/браузерный flow из Ebb.
- Управление пользовательским профилем Hermes (чтение/запись его конфига, auth, профилей).
- Инструменты «редактирования ключей» в UI (если не одобрено отдельно).
- Проксирование provider-трафика, кэширование ключей в БД, создание per-Run профилей Hermes.

## Решения по findings review (2026-10-23)

- **F1 (HIGH)** — env-инъекция ключей: адаптер расширяет allowlist ровно для зарегистрированных имён `keyEnv` выбранного провайдера (валидация; только для selected provider; отсутствие утечки в логи/артефакты — обязательный тест). «Сырых» неизвестных переменных не пропускать.
- **F2 (HIGH)** — отмена `HERMES_MODEL_OVERRIDE_UNSUPPORTED`: удаляется во всех точках (run-service.ts:199, hermes-run-selection.ts:34, routes/runs.ts:83) вместе с тестами и док-упоминаниями (README.md:373, 05-hermes.md:123) атомарно.
- **F3 (HIGH)** — resume: выбор провайдера/модели персистится в RunRequest/Run (колонка/ссылка на реестр) и используется при `resumeRun` (тот же выбор; при отсутствии — дефолт). spec §10.2/§13.1 амендируются: Ebb сравнивает только имена провайдера/модели (не credentials, не endpoint URL).
- **F4 (MEDIUM)** — fingerprint: `providerName`/`model` (имена, без секретов) включаются в контекстный hash с версионированием Context Builder; старые манифесты остаются валидными по хранимой версии (с сохранением парсинга старой v1-baseline — dual-version decode); resume-гейт — по персистенному hash; тесты стабильности/версионирования.
- **F5 (MEDIUM)** — первая задача плана IN-005: read-only probe/spike на установленном Hermes (взаимодействие `--ignore-user-config` с user `.env`, в-memory MCP-регистрацией, skills/project-trust, fallback) с acceptance-маркером; spike проверяет отображение `EBB_*` → стандартный env-ключ провайдера.
- **F6 (MEDIUM)** — имена переменных: Ebb хранит секреты под именами `EBB_*`; при запуске built-in провайдера Ebb эмитит **стандартную env-переменную провайдера** (например, `OPENAI_API_KEY` для built-in `openai-api`) в child-окружение — регистрация в allowlist по F1. Конвенция `EBB_*` исключает коллизию с пользовательским `.env`; программная проверка пользовательского `.env` не выполняется (запрет чтения).
- **F7 (MEDIUM)** — `.env` Ebb: путь — `EBB_ORCHESTRATOR_HOME/.env` (изолированно от репозитория; выбор пользователя), loader и приоритет vs системный env и Windows ACL (icacls/NTFS) — явные шаги плана IN-005.
- **F8 (LOW)** — документы: обновить README.md, 05-hermes.md, 02-current-state.md:150 и Plan20 (строки 210/251/263/269) — атомарно; UI-проекция исключает значения `keyEnv` (только имена/статус).

## Решения по re-review (2026-10-23)

- **F6 (уточнено):** для built-in провайдеров `key_env` Hermes не читается (registry фиксирует стандартные env-имена); Ebb эмитит стандартные env-переменные провайдера (регистрация в allowlist по F1). Пользовательские провайдеры с `key_env` — вне v1.
- **Кастомные провайдеры:** в v1 поддерживаются **только built-in провайдеры Hermes**. Пользовательские провайдеры (config-определённые/`key_env`) откладываются до подтверждения механизма доведения до Hermes под `--ignore-user-config` в отдельном шаге. Ebb-реестр в v1 ограничен built-in списком Hermes.
- **Amendment Plan20** — входит в scope IN-005: переформулировка Task5B/5C-контрактов (отмена `HERMES_MODEL_OVERRIDE_UNSUPPORTED`, разрешение явного выбора провайдера/модели через Ebb, env-передача ключей, отсутствие credential-дублирования в SecretStore/.env root; live-acceptance на пользовательском провайдере остаётся гейтом Plan20 после изменений).
