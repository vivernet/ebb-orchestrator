# Production ContextManifest lifecycle for every Run binding

**Goal:** Persist an accurate, durable `ContextManifest` for every production Task, Epic, and Request Run, and make its exact prepared-input provenance govern safe resume.

**Architecture:** A deterministic `RunContextAssembler` consumes validated persisted domain inputs plus each existing role-specific caller prompt, then produces the exact final prompt and provenance DTO. `RunService` persists one Run and its manifest atomically before any Scheduler/runtime dispatch; SQLite remains authoritative. Recovery may resume only the original Run and its original Hermes session after the persisted input fingerprint and execution boundary still match, the accessible workspace is unchanged, and the prior Hermes process is proven stopped. The verified Hermes Agent `v0.21.5+7357.g9244275` (source commit `9244275491ee0d5bc3481590b041114c4e1d399a`) accepts `hermes chat --query-file <path> --source <tag> --format stream-json` and emits/flushed a live `system/init.session_id` before credential and agent initialization. Task 5A is the provider-free supervised process-scope foundation; Task 5B must first make the approved Hermes-native per-Run profile/auth path safe, then add a bounded live JSONL observer, correlate the event to the durable Run owner, and compare-and-set the original ID while Hermes remains live. `hermes sessions list --source <tag>` is not a production capture mechanism: it is human-readable rather than JSON and can perform session-store side effects. Task 5C consumes only the durable session ID after restart and proven process stop. Hermes remains the sole owner of provider credential resolution. Each Run uses a fresh Hermes-native profile under the Hermes root that owns the configured auth store; it does not share the user's whole profile or copy auth files. Read only the explicitly configured, non-secret provider/model/endpoint selection through a pinned, bounded, side-effect-limited projection. Do not infer selection from auth status/list commands or silently switch to a fallback. Hermes itself resolves and refreshes credentials only through a native method supported by the pinned version and proven safe with this per-Run profile. Environment- or plugin-backed auth sources remain gated until separately proven. If selection, auth support, profile isolation, or native resolution is ambiguous or unsafe, fail closed before spawn. No provider-backed launch is enabled unless the bounded configuration, empty-plugin, profile-path, and real-provider gates pass.

**Authority:** User-approved `docs/architecture/proposals/08-production-context-manifest.md`; accepted Hermes provider-auth ownership direction in `docs/architecture/proposals/09-hermes-provider-auth-reuse.md`; `docs/architecture/specs/01-system-design.md`.

**Global Constraints:** Do not capture or claim hidden Hermes/system prompts, runtime-injected context, or Hermes conversation history. Do not backfill historical Runs with guessed manifests. Preserve each existing role's caller-owned prompt and mandatory structured inputs. A Run without its manifest is never dispatchable. Keep Run and manifest in one SQLite transaction. Persist the unique per-Run Hermes `source_tag`, native per-Run `HERMES_HOME`, containment identity, and launch nonce before spawn. Hermes owns provider configuration and native credential resolution/refresh. Do not add a duplicate Ebb SecretStore credential, Ebb provider-key environment injection, copied auth file, or shared whole user profile. Every Run uses an isolated fresh native Hermes profile beneath the root that owns the configured auth store. Preserve the explicitly configured provider/model/endpoint using only a bounded non-secret projection; never infer selection from auth status/list or silently fall back. Support only auth methods that the pinned Hermes version demonstrably resolves safely through that isolated profile; plugin- or environment-backed sources remain gated until separately proven. Hermes resolves credentials; Ebb never reads or copies credential values. Missing, unsupported, ambiguous, or unsafe auth/config/profile conditions fail closed before spawn. Profile creation and config reads must validate the native root and every path component without following symlinks/reparse points, enforce private per-Run ownership/ACLs, and use handle/descriptor-bound create/open/write/cleanup. If any platform cannot prove those controls, fail closed before Hermes spawn. A Hermes session ID is usable only when the version-pinned supervised process emits exactly one valid allowlisted `system/init.session_id` event while its exact durable owner is `LIVE`; correlate it to the immutable Run ID, `source_tag`, Hermes home, containment identity, and launch nonce, then compare-and-set `agent_runs.session_id` while that process remains alive. Persist capture validity separately from process state: after capture is `INVALID`, no later or stale callback may restore a resumable session. Missing, malformed, duplicate, out-of-bound, mismatched, or uncorrelated events and CAS failure fail closed. `hermes sessions list --source <tag>` is not a capture mechanism; do not use private Hermes SQLite, `latest`, inferred IDs, or post-close buffered stdout as authority. The bounded live observer may retain only the allowlisted session ID in memory long enough for the CAS and safe usage/status projection; never persist or expose raw JSONL stdout, event text/tool arguments, launch arguments, prompts, or potentially secret-bearing stderr in artifacts, logs, Run rows, or APIs. The controlled `submit_result` channel remains the authoritative structured role result; JSONL `result.text` is not authoritative. Only resume the same Run with the exact persisted session ID and exact prepared-input/execution fingerprint after authoritative proof the old process stopped; mismatch returns `RESUME_NOT_SAFE_WORKSPACE_CHANGED` and does not create or dispatch a concurrent Run. Keep exact unsupported token measurement `NULL`; never substitute a character/byte estimate. Use the approved repository configuration contract at `.ebb-orchestrator/project.yaml`; repository-authored changes remain untrusted candidates and must never be automatically applied. Context preparation binds only the active, explicitly approved Project Config revision/hash. Do not add `.orchestrator/` discovery or migration behavior. Preserve permission, approval, Scheduler, budget, and Git ownership boundaries; no provider/hosted CI actions are assumed approved by this plan.

**Provider identity for resume:** Bind only stable, non-secret provider/model/endpoint identity explicitly exposed by the pinned Hermes version's supported configuration projection. The endpoint identity/revision must be source-backed and mutation-sensitive: it must change whenever the effective endpoint changes, including a change to `api`/`base_url` under an unchanged provider alias. A provider or endpoint alias alone is insufficient when the effective endpoint can change beneath it. Never persist the endpoint URL or derive identity by hashing it. Do not introduce an Ebb-generated HMAC/fingerprint key, an Ebb SecretStore entry, a root `.env` value, or a user-supplied parallel mapping. If the pinned Hermes configuration exposes no source-backed revision/identity with this mutation guarantee, fail closed before creating the Run or manifest and record a sanitized `HERMES_ENDPOINT_ID_UNAVAILABLE` reason; do not spawn Hermes, retain the URL, or claim provider acceptance. This fail-closed case is an explicit supported outcome, not a missing fallback to implement.

**Windows path ancestry contract:** Do not modify any Windows ACL to make Hermes acceptance pass. A broader DACL is potentially acceptable only on lexical ancestors strictly above the auth-owning Hermes root. When evaluating an ancestor handle, skip only ACEs carrying `INHERIT_ONLY_ACE`, since they do not apply to that handle; inspect every other ACE according to its type. Apply the bounded rights check to each effective foreign `ACCESS_ALLOWED_ACE`: its mask may contain only this exact set: `FILE_ADD_FILE | FILE_ADD_SUBDIRECTORY | FILE_TRAVERSE | FILE_READ_ATTRIBUTES | FILE_LIST_DIRECTORY | FILE_READ_EA | READ_CONTROL | SYNCHRONIZE`; `FILE_LIST_DIRECTORY` and `FILE_READ_EA` are additionally tolerated read-only rights, and the latter six rights are limited to opening/traversing the named child relative to its pinned parent, listing that ancestor when required by native path traversal, reading basic attributes or EA metadata, querying identity/DACL, and retaining a synchronous handle. Generic/unknown rights and mutation rights beyond the already bounded child-add rights `FILE_ADD_FILE | FILE_ADD_SUBDIRECTORY` in such an effective foreign allow ACE remain fail-closed. Preserve the native verifier's existing treatment of effective `ACCESS_DENIED_ACE` and `SYSTEM_AUDIT_ACE`; their masks are not subjected to this allow-ACE rights check. Unknown or compound ACE types remain fail-closed. On the auth-owning Hermes root and every descendant, the existing strict owner/private or mutation-safe ACL requirements remain unchanged; the two additional read-only rights do not extend to those objects, and each descendant component's applicable ACL is checked separately under its own policy. Tolerating even the bounded ancestor set requires the implementation to open the volume/root and every ancestor sequentially relative to its held parent handle with no-follow/no-reparse semantics, capture each component's volume/file identity, bind the complete chain to the Run's one-use launch authorization, and reopen/recheck every identity before each path-based boundary. The native launch supervisor must hold no-delete-sharing handles for that same verified chain from before process creation through authoritative `STOPPED`; any incompatible existing handle, open failure, identity mismatch, or missing stop proof fails closed. A no-delete-share handle is not treated as an ACL freeze: the tests must establish that allowed child additions cannot win a missing Run-leaf name, alter the selected object, or redirect later opens, while delete/reparse/ACL-change attempts are denied or cause pre-resume rejection. The auth-owning Hermes root, its `profiles` directory, the per-Run profile, `home`, `config.yaml`, Hermes source/executable/runtime objects, and any other target files retain their strict owner/private or mutation-safe ACL requirements. Creation, projection, launch, and cleanup must use handle-relative operations for the exact objects whose identities were checked; a prior string-path check or leaf-only identity is insufficient. These controls address namespace replacement, not hostile same-user mutation, and do not claim an OS sandbox. If the complete chain cannot be captured, bound, and revalidated across the helper-to-supervisor boundary, Windows fails closed; do not weaken the existing ACL gate as a partial workaround.

For the Windows launch ticket, the per-Run target identity binding is exactly `{ home: { volumeSerial, fileId }, config: { volumeSerial, fileId } }`, captured after both objects exist by the native no-follow verifier without reading `config.yaml`. The bounded EBB3 frame carries those four lowercase fixed-width identifiers adjacent to `profileHomeIdentity`. The supervisor opens `home` and `config.yaml` relative to the pinned Run-profile handle, verifies their types, strict private owner/DACL policy, single-link file property for `config.yaml`, and exact ticket identities before process creation and again immediately before resuming the suspended Hermes process. It holds the target handles through the Job's authoritative empty/STOPPED observation. Target-open, ACL, identity, or recheck failure terminates the still-suspended child and fails closed.
