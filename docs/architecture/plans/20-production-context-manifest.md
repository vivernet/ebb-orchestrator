# Production ContextManifest lifecycle for every Run binding

**Goal:** Persist an accurate, durable `ContextManifest` for every production Task, Epic, and Request Run, and make its exact prepared-input provenance govern safe resume.

**Architecture:** A deterministic `RunContextAssembler` produces exact prompt/provenance, and `RunService` commits each Run and its single manifest atomically before dispatch. Windows/Linux same-Run recovery remains governed by the existing durable session, manifest/workspace, Scheduler, and full platform-scope STOPPED gates. macOS 13.5+ Apple Silicon (`arm64`) ordinary Hermes Runs use the accepted direct-host bounded process-group contract in Proposal17. A generation-bound native anchor is the live group leader, gates payload launch until durable ACK, self-signals only its own group, and self-stops on control-channel EOF; Ebb never signals numeric PID/PGID. Deliberately detached descendants are out of guarantee. macOS failure never auto-resumes the old logical Run/session; verified group-empty or changed boot-session evidence allows existing unsuccessful terminal reconciliation, while same-boot ambiguity remains UNKNOWN with owner/capability/reservation/locks held. No reconnect daemon, VM/profile, new recovery UI/state/override, or Hermes credential/config management is introduced. Hermes uses its existing user root/profile and native auth; Ebb does not read/copy/change that setup. Existing in-memory Ebb MCP registration and live `system/init.session_id` capture remain required. Proposal06 approved Epic phase-intent recovery and Coordinator/Scheduler generation CAS remain unchanged. Task5B still needs real provider-backed capture; Plan20 Task7 and platform gates remain independent.

**Authority:** Proposal08, Proposal09 amendment, spec-01 and accepted Proposal17 (user decision 2026-10-16; independent architecture/security review `APPROVED`). Proposal15 is retained as superseded history, not active design. Proposal13 continues to prohibit host ACL/owner/foreign-grant inventory/remediation. Plan20 remains `in_progress`; this approval does not close any plan, task, checklist, or downstream status.

**macOS support target and accepted v1 behavior:** macOS 13.5+ on physical Apple Silicon (`arm64`); Intel is outside scope. Ordinary Runs invoke the installed Hermes through the existing Hermes root/profile and auth. The exact controlled boundary is the bound runner plus its original process group, supervised by a first-party anchor. `COMPLETED` requires valid Hermes result and verified empty bound group; deliberate detached descendants may survive and remain outside guarantee. For interruption, no same-Run `--resume` or automatic same-Run redispatch; manual Hermes actions outside Ebb are not OS evidence. On same-boot ambiguity, keep UNKNOWN and all owner/capability/reservation/resource locks; allow release only after exact `DARWIN_GROUP_EMPTY` or verified old/current boot-session UUID mismatch (`BOOT_SESSION_CHANGED`) through existing reconciliation. Ebb performs no external numeric PID/PGID signal, no reconnect, and no owner override. On Ebb EOF the anchor closes its gate and runs the same TERM/grace/self-KILL group path. Existing Proposal06 Epic phase-intent flows continue under their existing Coordinator/Scheduler/generation CAS and the common owner preflight. **Design accepted/reviewed; implementation and macOS CI/provider acceptance are OPEN.**

**Accepted macOS design (2026-10-16):** [Proposal17](../proposals/17-macos-direct-host-hermes-runtime.md) authorizes direct host runtime for ordinary Hermes Runs on physical Apple Silicon `arm64`, macOS 13.5+. Independent architecture/security review is `APPROVED`. The supported boundary is the first-party anchor and its original process group; deliberate detached descendants are outside the guarantee. The user explicitly accepted this narrower boundary. This acceptance authorizes implementation planning, not implementation itself. The production source, native helper, migration, and CI remain untouched until a fresh Plan20 review approves this plan.



**Dependency boundary:** Plan05, Plan06, and Plan19 remain downstream consumers of Plan20 and keep their own statuses until their own evidence/review gates pass; they are not prerequisites. The accepted macOS design adds only the migration/interface and platform acceptance tasks below. Preserve every `context_deltas` row, value, FK action, index, root page, and diagnostic-only meaning; do not rebuild or copy that table.

**Global Constraints:** Do not capture or claim hidden Hermes/system prompts, runtime-injected context, or Hermes conversation history. Do not backfill historical Runs with guessed manifests. Preserve each existing role's caller-owned prompt and mandatory structured inputs. A Run without its manifest is never dispatchable. Keep Run and manifest in one SQLite transaction. Persist the unique per-Run Hermes `source_tag`, containment identity, and launch nonce before spawn. Per Plan24 (accepted 2026-10-23), Ebb owns the full provider/model configuration catalog (all 86 LobeHub-pinned provider IDs) and its Web-managed auth lifecycle; Hermes remains the default runtime. Plan20 keeps its process-supervision and reconciliation invariants and no longer treats Hermes as the only provider configuration owner. Do not add a duplicate Ebb credential, provider-key environment injection, or copied user Hermes config/auth. Use the existing user-configured Hermes root/profile for every invocation. Register existing Ebb MCP tools in memory through the supported API for the installed Hermes CLI; do not add a profile/config overlay or another configuration subsystem. Do not parse auth files or inspect credential values. Do not replace Hermes' configured provider/model. The bounded live observer may persist only the allowlisted session ID after correlating the exact Run, owner, source tag, containment identity, and launch nonce while the process is `LIVE`; missing, malformed, duplicate, out-of-bound, mismatched, uncorrelated events or CAS failure fail closed. `hermes sessions list` and post-close buffered stdout are not capture authority. Never persist or expose raw JSONL stdout, event text/tool arguments, prompts, or potentially secret-bearing stderr in artifacts, logs, Run rows, or APIs. `submit_result` remains the authoritative structured role result. Resume only the same Run and exact persisted session after authoritative old-process STOPPED proof, available fingerprint checks, and unchanged workspace. Hermes resolves the current provider/model/auth from its existing configuration; Ebb does not compare, inspect, or require provider-context identity for resume. Keep exact unsupported token measurement `NULL`; never substitute a character/byte estimate. Use the approved repository configuration contract at `.ebb-orchestrator/project.yaml`; repository-authored changes remain untrusted candidates and must never be automatically applied. Context preparation binds only the active, explicitly approved Project Config revision/hash. Do not add `.orchestrator/` discovery or migration behavior. Preserve permission, approval, Scheduler, budget, and Git ownership boundaries; no provider/hosted CI actions are assumed approved by this plan.

**Provider identity for resume:** Provider/model/context identity is outside Ebb's resume gate. Ebb uses the same durable Run/session and validates its own manifest/workspace/process state, then invokes Hermes resume through the user's configured root/profile. Hermes applies its current provider/model/auth settings. Ebb does not inspect Hermes config, require a context revision, hash/persist endpoint URLs, or create identity keys/mappings. This means provider settings may have changed since the original Run; Hermes owns that routing behavior. Per Plan24, Ebb persists the selected provider/model/auth-method/config-revision in the Run and passes it at dispatch/resume; missing explicit selection falls back to the Hermes default runtime. Resume eligibility remains gated on Ebb's durable Run/session/manifest/workspace/stop evidence, never on provider configuration identity.

**Hermes host-path compatibility (user decision 2026-10-10):** Use the existing configured Hermes root/profile. Do not inventory or validate ACL/DACL, owner, mode, or foreign grants on host/Hermes paths or Ebb-owned host paths; do not change permissions. Keep only ordinary exact-path, expected-file-type, and no-follow checks directly required for process launch or cleanup. There is no per-Run Hermes profile, profile identity chain, profile-private permission contract, or profile cleanup requirement. Proposal13 is not authority to reintroduce such checks.

For the Windows launch ticket, no Hermes Run-profile/home/config identity is captured. Keep only the native process-scope identity and authoritative STOPPED proof required by Task5A, plus ordinary executable/path/type checks needed to launch the installed runtime. Do not add ACL/DACL, owner, or profile-chain checks for the user Hermes root/profile or temporary Ebb artifacts.

### Historical Hermes source re-audit (2026-10-08; superseded contract)

**Historical runtime-source inspection (diagnostic only; source pin superseded 2026-10-10):** Inspection of the installed Hermes checkout recorded commit `08165d58931841cee713468ae89032af7c57060a` and version `v0.21.5+9117.g08165d5`. The `hermes chat --query-file <path> --provider <provider_id> --model <model_id> --source <tag> --format stream-json` transport and flushed early `system/init.session_id` contract remain present. The audited CLI fallback path can change `requested_provider` to the selected fallback entry; it is therefore not proof of the provider that actually served the Run. The initial acceptance proposal therefore required an independent final-provider observer; the 2026-10-08 source-backed explicit-provider/no-fallback policy below supersedes that requirement, because stream-json exposes no provider field. The stream `system/init` event contains `model` and `session_id`, but no provider field, so it cannot by itself prove provider identity. Current Hermes profile auth is not credential-isolated: provider state checks the fresh profile first, then falls back per provider to the Hermes global-root `auth.json`; credential-pool lookup has corresponding read-only root fallback, and refresh writes back through the store Hermes selected. The accepted route is Hermes-native global/default auth fallback, with no copied auth files or Ebb credential store. The current source still supports source-pinned provider endpoint/env-name projection; any config or runtime endpoint override remains fail-closed, and custom/private endpoints without a stable source identity remain unsupported. This is source-contract evidence only; no auth/config store was read, no provider was invoked, and no live provider acceptance is implied.

**2026-10-08 provider-route audit (historical evidence; superseded by Proposal09 amendment 2026-10-10):** Read-only inspection at exact Hermes source commit `08165d58931841cee713468ae89032af7c57060a` confirmed chat `--provider` and `--model` are supported and explicit CLI arguments precede profile config selection.
