# Ebb Orchestrator — проверка и исправление политики AGENTS

> **Для агента-рецензента:** это проверка политики с правом редактирования. Рецензент обязан не только перечислить ошибки, но и самостоятельно исправить файлы `AGENTS.md`/roadmap/docs-политику, если корректное решение однозначно следует из текущей реализации и утверждённой архитектуры.

## Цель

Проверить финальные инструкции репозитория Ebb Orchestrator уже внутри реального проекта после v1 и Final Audit, устранить противоречия, устаревшие утверждения, избыточность и опасные инструкции.

## Область

Рецензент имеет право изменять:

- `/AGENTS.md`
- `/apps/server/AGENTS.md`
- `/apps/web/AGENTS.md`
- `/packages/contracts/AGENTS.md`
- `/docs/roadmap/post-v1.md`
- ссылки на документацию, если путь реально изменился

Рецензент не изменяет боевой код, тесты, миграции, зависимости или конфигурацию времени запуска в рамках этой проверки.

Если для исправления политики требуется изменение боевого кода — оформить проблему, не выполнять его.

## Источники авторитета

Проверять инструкции против:

1. фактического текущего кода;
2. утверждённой спецификации архитектуры;
3. каноническим планам 1–6;
4. отчёту Final V1 Audit & Hardening;
5. текущего `README.md`;
6. актуального руководству по стилю JSDoc;
7. фактических скриптам и конфигурации пакетов.

Код и утверждённая архитектура важнее устаревшей формулировки в AGENTS.

## Правила проверки

Все пользовательские ответы и замечания рецензирования писать на русском языке.

Не принимать текст AGENTS на веру.

Для каждого существенного правила ответить:

- соответствует ли оно реальному коду;
- относится ли к этому области задачи;
- не противоречит ли parent/scoped AGENTS;
- не создаёт ли два источника истины;
- не заставляет ли агента делать лишнюю работу на каждой задаче;
- можно ли выполнить правило однозначно;
- не даёт ли инструкция опасно широкие права.

## Обязательные проверки

### 1. Иерархия

Проверить:

```text
/AGENTS.md
/apps/server/AGENTS.md
/apps/web/AGENTS.md
/packages/contracts/AGENTS.md
```

Файлы scoped должны дополнять root и не менять глобальные инварианты.

Устранить дублирование, если оно не нужно для безопасности.

### 2. Идентичность проекта

Выполнить поиск устаревших идентификаторов по всему репозиторию и проверить каждый результат:

```text
@orchestrator/
local-ai-development-orchestrator
local-ai-development-orchestrator-design
```

Если это текущий идентификатор пакета/проекта — заменить на актуальный `@ebb-orchestrator/*` / `ebb-orchestrator`. Если это историческое имя уже существующего файла или артефакта миграции, не переименовывать автоматически: сначала проверить реальные ссылки и историю Git.

Везде использовать актуальное имя:

`Ebb Orchestrator`

Удалить старые названия, если они используются как текущее название продукта.

### 3. Политика ветки/worktree

Проверить, что:

- ветка по умолчанию действительно `master`;
- рабочий процесс worktree соответствует текущему процессу;
- инструкции не разрешают деструктивные операции Git без одобрения;
- политику завершения соответствует фактическим контрольными этапами качества.

### 4. Контрольные этапы качества

Сверить:

- `pnpm lint`;
- `pnpm typecheck`;
- `pnpm test`;
- командами сборки/E2E.

Если AGENTS требует несуществующую команду — исправить инструкцию, а не выдумывать скрипт.

### 5. Архитектура

Проверить формулировки:

- deterministic-first;
- модульный монолит;
- Ports & Adapters;
- Git vs SQLite источника истины;
- границе AI/домена;
- ответственности Scheduler/Workflow;
- approvals;
- recovery;
- AgentRuntime abstraction.

Удалить утверждения, которые не реализованы и не являются обязательным инвариантом архитектуры.

### 6. Безопасность

Особенно проверить:

- Action Gateway;
- Permission Engine;
- содержимое репозитория как недоверенный ввод;
- Local Mode != OS sandbox;
- secrets;
- shell/process;
- Git hooks/network;
- финального одобрения слияния.

Если формулировка создаёт ложное чувство гарантии песочницы/безопасности — исправить.

### 7. Правила scoped backend

Проверить `apps/server/AGENTS.md` по реальной архитектуре backend:

- границы модулей;
- сохранение данных;
- outbox/jobs;
- startup;
- Git;
- Hermes;
- граница разрешений.

- Не оставлять правила для подсистемы, которой в v1 нет.

### 8. Правила scoped web

Проверить:

- авторитет backend;
- фактической архитектуре API/SSE;
- текущем стеке frontend;
- команды сборки/тестов;
- UX безопасности.

### 9. Граница contracts

Проверить фактические зависимости `packages/contracts`.

Если имя пакета/рабочей области изменился — исправить команды.

Не разрешать contracts → server dependency.

### 10. Roadmap

`docs/roadmap/post-v1.md` должен содержать только будущие направления, а не реализованные features v1.

Проверить по Final Audit, не была ли какая-то roadmap-функция уже реализована.

Если была — перенести/удалить её из списка будущих задач.

Не добавлять новые идеи продукта без основания в исходной истории design/planning.

### 11. Эффективность контекста

Корневой `AGENTS.md` должен оставаться достаточно коротким для постоянного включения в контекст агента.

Удалить:

- подробные разделы учебника;
- длинные повторения спецификации архитектуры;
- историю реализации;
- сведения, которые нужны только одному подсистемы.

Заменять их ссылкой на канонический документ.

### 12. Качество инструкций

Каждое обязательное правило должно быть:

- конкретным;
- проверяемым;
- непротиворечивым;
- актуальным;
- относящимся к агентам разработки.

Избегать расплывчатых формулировок вроде:

- «писать хороший код»;
- «учитывать безопасность»;
- «использовать лучшие практики».

## Политика редактирования

Рецензент МОЖЕТ самостоятельно исправить:

- устаревший путь/имя;
- неверную команду;
- дублирование;
- противоречие между parent/scoped AGENTS;
- формулировку инварианта безопасности;
- неверный claim о текущей реализации;
- слишком длинный/шумный раздел;
- неправильное размещение правила между root/scoped-файлом;
- пункт roadmap, который уже реализован в v1;
- неработающей ссылки на документацию.

Рецензент НЕ МОЖЕТ самостоятельно менять:

- архитектуру;
- области задачи;
- семантику безопасности;
- требования одобрения;
- обязанности ролей;
- Git workflow политику,

если для этого нет однозначного основания в утверждённой архитектуре/текущей реализации.

Такое изменение оформить как:

`REQUIRES HUMAN DECISION`.

## Проверка

После правок:

```bash
git diff --check
git status --short
```

Проверить все относительные пути из AGENTS/roadmap.

Проверить, что изменения AGENTS не затронули боевой код.

Если в репозитории есть проверка Markdown/ссылок — выполнить её.

## Независимая проверка согласованности

После собственных исправлений перечитать все четыре AGENTS в порядке:

1. root;
2. server;
3. web;
4. contracts.

Представить мысленно три задачи:

- исправление ошибки безопасности backend;
- изменение UI frontend;
- изменение общего контракта.

Для каждой убедиться, что объединённый набор инструкций не содержит конфликтов и даёт однозначный workflow.

## Коммит

Если правки выполнены:

```text
docs: review and correct agent policies
```

## Финальный отчёт

На русском языке сообщить:

- какие файлы проверены;
- какие проблемы найдены;
- что исправлено автоматически;
- какие правила удалены как избыточные;
- какие claims исправлены по реальному коду;
- есть ли `REQUIRES HUMAN DECISION`;
- SHA финального коммита;
- `git status --short`.

Статус только один из:

```text
AGENTS_POLICY_APPROVED
AGENTS_POLICY_APPROVED_WITH_PROPOSALS
AGENTS_POLICY_BLOCKED
```

Не выполнять merge и не отправлять изменения.
