# Documentation Governance — Checklist & Implementation

**Версия:** 1.0  
**Дата утверждения:** 2026-09-23

---

## Цель

Этот документ фиксирует чеклист и инструкции по реализации политики документации, описанной в `01-documentation-governance.md`.

## Контракт metadata для Plan

Plan — единственный источник идентичности и зависимостей: используются `id` и `depends_on`; дополнительных полей для roadmap/stage-группировки нет. Этот контракт не нормализует метаданные и статусы документов других `kind`.

```ts
type PlanStatus = 'proposed' | 'planned' | 'in_progress' | 'blocked' | 'completed' | 'superseded' | 'cancelled';

interface PlanMetadata {
  id: string;
  kind: 'plan';
  status: PlanStatus;
  title: string;
  created: string; // Дата календаря ISO YYYY-MM-DD
  updated: string; // Дата календаря ISO YYYY-MM-DD
  summary?: string;
  depends_on?: string[];
  specs?: string[];
  evidence?: string[];
}
```

Парсер обязан проверять наличие и тип каждого обязательного поля, `kind`, статус и реальные календарные даты; если необязательное поле присутствует, оно также проверяется по указанному типу. Некорректные значения отклоняются, а не преобразуются.

## Каноническая политика именования

Числовой префикс используется только для нескольких документов одного типа, образующих упорядочиваемую серию. Уникальный документ получает описательное имя без префикса. `README.md` остаётся без префикса и YAML frontmatter.

Для Plan идентичность определяется только Plan ID, а зависимости — только `depends_on`; дополнительные roadmap/stage metadata или отдельная группировка не используются. Lifecycle enum применяется только к `kind: plan`: допустимы статусы `proposed`, `planned`, `in_progress`, `blocked`, `completed`, `superseded`, `cancelled`. Документы других `kind` сохраняют собственные статусы (например, `kind: ledger` со статусом `draft`) без нормализации и проверки по Plan enum.

Сгенерированные roadmap-файлы изменяются только запуском предусмотренного генератора. Это правило документации не меняет значения или семантику runtime workflow.

## Правила нумерации

### Файловая нумерация
Префикс используют только участники повторяющейся упорядочиваемой серии однотипных документов; уникальные документы не нумеруются:

| Префикс | Тип документа | Пример |
|---------|---------------|--------|
| `01-`, `02-` | Члены упорядочиваемой серии однотипных документов | `01-system-design.md`, `02-system-design.md` |
| без префикса | Уникальный документ | `merge-decisions.md` |
| без префикса | Индекс README (исключение) | `README.md` |

### Внутренняя нумерация разделов
Нумерация разделов независима от префикса имени файла и отражает только структуру документа:

```markdown
## 1. Purpose
## 2. Scope
## 3. Numbering Rules
```

### Даты и история
- Обновляйте `updated:` в YAML metadata при изменениях контента
- Сохраняйте исходные даты в metadata и историческом тексте, а не используйте дату как filename-префикс

## Правила именования

### Файлы
- Используйте строчные буквы с дефисами в описательной части имени
- Добавляйте числовой префикс только при принадлежности к упорядочиваемой серии однотипных документов
- Для уникальных документов используйте описательное имя без префикса
- Оставляйте `README.md` без префикса и frontmatter
- Избегайте пробелов, подчеркиваний или специальных символов
- Имена должны быть описательными, но не более 50 символов

### Директории
- Группируйте по функциональности: `architecture/`, `development/`, `audit/`, `reference/`, `roadmap/`
- Названия директорий должны быть в единственном числе

### YAML Metadata
Plan-документы должны соответствовать контракту Plan metadata выше. Документы иных `kind` не обязаны использовать Plan lifecycle enum; их metadata и статусы сохраняются согласно их собственному типу.

Plan frontmatter:
```yaml
---
id: <уникальный идентификатор>
status: in_progress
kind: <тип документа: Plan|Spec|Audit|Guideline|Ledger|Reference>
title: <описательный заголовок>
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```

## Правила Валидации

### Обязательные проверки
Каждый документационный файл должен пройти:

1. **Префикс filename**: требуется только для члена упорядочиваемой серии однотипных документов; для уникальных документов не требуется. `README.md` остаётся без префикса.
2. **Metadata**: проверяйте по контракту соответствующего `kind`; Plan lifecycle enum применяется только к `kind: plan`
3. **Plan ID и зависимости**: `id` идентифицирует Plan, `depends_on` задаёт зависимости; дублирующую группировку не вводить
4. **Даты Plan**: `created:` и `updated:` должны быть реальными календарными датами `YYYY-MM-DD`

### Скрипт валидации
Используйте инструменты валидации проекта для проверки соответствия:
- Запустите `pnpm docs:check` в директории документации
- Исправьте все помеченные нарушения перед коммитом

### Статус соответствия
| Статус | Значение |
|--------|----------|
| Compliant | Все правила валидации прошли |
| Non-compliant | Одно или несколько правил не пройдено |
| Deprecated | Более не используется активно |

## Чеклист создания нового документа

### 1. Определение типа документа

- [ ] Определить тип (Plan/Spec/Audit/Guideline/Ledger/Reference)
- [ ] Выбрать правильную директорию согласно политике

### 2. Формирование имени файла

- [ ] Использовать числовой prefix только для члена упорядочиваемой серии однотипных документов
- [ ] Для уникального документа использовать описательное имя без prefix; для README — `README.md` без frontmatter
- [ ] Использовать kebab-case для описания
- [ ] Избегать дат в имени файла
- [ ] Избегать терминов v1, post-v1, next, current в имени


### 3. Добавление YAML metadata

- [ ] Для Plan добавить обязательные поля Plan metadata (id, kind, status, title, created, updated)
- [ ] Проверить соответствие формата id схеме
- [ ] Проверить значение kind в enum
- [ ] Не применять Plan lifecycle enum к документам другого `kind`
- [ ] Добавить опциональные поля (depends_on, specs, evidence, summary)

### 4. Валидация

- [ ] Запустить `pnpm docs:check`
- [ ] Проверить все сообщения об ошибках
- [ ] Исправить выявленные проблемы
