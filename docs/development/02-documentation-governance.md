# Documentation Governance — Checklist & Implementation

**Версия:** 1.0  
**Дата утверждения:** 2026-09-23

---

## Цель

Этот документ фиксирует чеклист и инструкции по реализации политики документации, описанной в `01-documentation-governance.md`.

---

## Правила Нумерации

### Файловая нумерация
Все документационные файлы используют 2-значный числовой префикс:

| Префикс | Тип документа | Пример |
|---------|---------------|--------|
| `01-` | Первичные спецификации и базовые документы | `01-system-design.md` |
| `02-` | Вторичные спецификации и детальные реализации | `02-documentation-governance.md` |
| `03-` | Справочные материалы и дополнительные стандарты | `03-production-readiness-design.md` |
| `20-` | Документы аудита и состояния проекта | `2026-09-18-audit-report.md` |

### Внутренняя нумерация разделов
Внутри документов нумерованные разделы должны согласовываться с файловой нумерацией:

```markdown
## 1. Purpose
## 2. Scope
## 3. Numbering Rules
```

### Отслеживание версий
- Обновляйте `updated:` в YAML metadata при изменениях контента
- `last_updated:` должен отражать дату последней модификации

---

## Глоссарий

| Термин | Определение |
|--------|-------------|
| Governance | Стандарты документации и требования соответствия |
| Spec | Официальная архитектурная или дизайн спецификация |
| Plan | Путь реализации, выведенный из спецификаций |
| Audit | Проверка и валидация состояния проекта |
| Artifact | Любой задокументированный результат (документ, код, конфигурация) |

---

## Правила Именовани

### Файлы
- Используйте строчные буквы с дефисами: `01-documentation-governance.md`
- Избегайте пробелов, подчеркиваний или специальных символов
- Имена должны быть описательными, но не более 50 символов

### Директории
- Группируйте по функциональности: `architecture/`, `development/`, `audit/`, `reference/`, `roadmap/`
- Названия директорий должны быть в единственном числе

### YAML Metadata
Все документы должны содержать обязательные поля:
```yaml
---
id: <уникальный идентификатор>
kind: <тип документа: Plan|Spec|Audit|Guideline|Ledger|Reference>
title: <описательный заголовок>
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```

---

## Правила Валидации

### Обязательные проверки
Каждый документационный файл должен пройти:

1. **Валидация префикса**: 2-значный числовой префикс должен присутствовать
2. **Наличие YAML metadata**: Блок YAML frontmatter должен быть в начале файла
3. **Поле id**: Должно быть непустым и соответствовать схеме
4. **Поле kind**: Должно быть из разрешенного enum значений
5. **Поля даты**: `created:` и `updated:` должны быть валидными датами

### Скрипт валидации
Используйте инструменты валидации проекта для проверки соответствия:
- Запустите `pnpm docs:check` в директории документации
- Исправьте все помеченные нарушения перед коммитом

### Статус соответствия
| Статус | Значение |
|--------|----------|
| Compliant | Все правила валидации прошли |
| Non-compliant | Одно или несколько правил не пройдено |
| Deprecated | Более не используется активно |

## Чеклист создания нового документа

### 1. Определение типа документа

- [ ] Определить тип (Plan/Spec/Audit/Guideline/Ledger/Reference)
- [ ] Выбрать правильную директорию согласно политике

### 2. Формирование имени файла

- [ ] Использовать 2-значный числовой prefix
- [ ] Использовать kebab-case для описания
- [ ] Избегать дат в имени файла
- [ ] Избегать терминов v1, post-v1, next, current в имени
- [ ] Избегать Phase в заголовках (использовать Stage)

### 3. Добавление YAML metadata

- [ ] Добавить обязательные поля (id, kind, title, created, updated)
- [ ] Проверить соответствие формата id схеме
- [ ] Проверить значение kind в enum
- [ ] Добавить статус, если применимо
- [ ] Добавить опциональные поля (depends_on, specs, evidence, summary)

### 4. Валидация

- [ ] Запустить `pnpm docs:check`
- [ ] Проверить все сообщения об ошибках
- [ ] Исправить выявленные проблемы
