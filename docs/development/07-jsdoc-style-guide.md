# Руководство по русскому JSDoc

## Область применения

Руководство распространяется на собственный production-код в
`apps/server/src/`, `apps/web/src/` и `packages/*/src/`. Тесты, fixtures,
generated-файлы и vendor-код не входят в обязательное покрытие.

JSDoc пишется на грамотном русском языке. Имена классов, методов, API,
полей, enum, состояний, команд, путей и других технических идентификаторов
не переводятся.

## Когда комментарий обязателен

Документируйте экспортируемые классы, функции, React-компоненты и hooks,
публичные интерфейсы, доменные type aliases и enums, публичные методы
сервисов и адаптеров, а также код с важными побочными эффектами,
предусловиями, ошибками или инвариантами.

Отдельно описывайте security-sensitive код, `Action Gateway`, `Permission
Engine`, Git/worktree/reconciliation, workflow transitions, recovery,
budget/concurrency/resource locks, persistence, Hermes/runtime/context/MCP и
сложные внутренние алгоритмы.

Очевидные private accessors, trivial mappers и локальные helpers без
неочевидного контракта обычно не требуют JSDoc.

ESLint автоматически требует JSDoc для публичных классов и функций в
production source. Интерфейсы, type aliases, enums, hooks и публичные методы
дополнительно документируются вручную, когда описывают доменный контракт или
неочевидный lifecycle; текущая конфигурация не пытается считать все
TypeScript-декларации через `require-jsdoc`, чтобы не создавать ложные
срабатывания для локальных типов.

## Содержание и теги

Сначала объясняйте назначение и причину существования компонента, затем —
инварианты, побочные эффекты, границы доверия, предусловия и значимые ошибки.
Не пересказывайте TypeScript-сигнатуру и не дублируйте типы в `{Type}`.

- `@param` описывает смысл параметра, если он не очевиден.
- `@returns` объясняет смысл результата, когда его нельзя вывести из имени.
- `@throws` перечисляет только значимые ошибки, которые действительно
  выбрасываются реализацией.
- `@example` добавляется только если пример упрощает использование.
- `@deprecated` используется только для реально устаревшего API.

Описание каждого присутствующего тега должно быть полным предложением на
русском языке.

## Примеры

Плохо:

```ts
/** Возвращает проект. */
export function getProject(id: string): Project { /* ... */ }
```

Хорошо:

```ts
/**
 * Загружает проект как авторитетный контекст оркестрации.
 * Репозиторный `.orchestrator`-конфиг не считается доверенным до определения
 * trust level проекта.
 *
 * @param id Идентификатор проекта в локальном состоянии Orchestrator.
 * @returns Запись проекта с вычисленным trust level.
 * @throws {ProjectNotFoundError} Если проект отсутствует в локальном состоянии.
 */
export function getProject(id: string): Project { /* ... */ }
```

### Security

Описывайте trust boundary, недоверенный ввод, смысл `ALLOW`, `ASK`, `DENY` и
`ABSOLUTE_DENY`, а также проверки, которые нельзя обходить. Не обещайте
изоляцию ОС, если код обеспечивает только изоляцию политик.

### Git

Указывайте целевой repository/worktree, hooks и сетевые побочные эффекты,
семантику журнала и reconciliation, а также постусловия операции.

### Workflow и persistence

Для переходов указывайте допустимое исходное и целевое состояние, guards,
approvals и сохраняемый invariant. Для сохранения данных фиксируйте границу
транзакции и idempotency, если они неочевидны.

### Hermes

Различайте `AgentRuntime`, профиль, session, context и capability. Отделяйте
авторитетный структурированный результат `submit_result` от
диагностического stdout/stderr.

## Факты и findings

Не выдумывайте поведение и не исправляйте функциональные дефекты в проходе
документации. Если назначение или инвариант нельзя доказать по реализации,
спецификации или тестам, оставьте комментарий минимальным и оформите finding:
модуль, серьёзность, наблюдение, доказательства и предлагаемое продолжение.

## Новые API

Новый экспортируемый API добавляется сразу с полезным русским JSDoc. Сначала
опишите назначение и контракт, затем добавьте только необходимые теги; не
добавляйте фиктивные `@returns`, `@throws` или `@example` ради lint.
